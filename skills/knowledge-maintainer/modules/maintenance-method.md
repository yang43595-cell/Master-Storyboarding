# 知识维护方法

0. **先分读取与写入根**：云端 release 只读；cloud-owned 案例只按其来源方明确授权的 sources/author/publish/verify 流程处理。当前仓库没有可读取的云端手册，遇到流程缺口时报告缺项，不猜路径、旧 pin 或发布规则；local-owned 方法仍走本地授权治理。云端整项目归档目的地未约定时报告待指定。
1. **先分属地**：专业理论、导演方法、对白方法、镜头知识和生成经验归 Vault；平台参数、CLI 边界、阶段输入输出、技术检查表和模板归对应 Skill。
2. **先查来源**：确认原始来源、现有主题页、canonical key 与规则状态，避免把同一结论写成多个规则。
3. **再查冲突**：`confirmed` 优先；两个 `confirmed` 结论冲突时停止写入并报告。
4. **再定可达性**：规则必须有真实消费者，并以其 profile topic 交集或明确 trigger 形成现有审计支持的可达路径；reference 类知识须有明确触发词。不为满足文字而添加无关宽泛 topic。
5. **只改唯一真相**：已有主题页可承载时更新原规则；确有独立语义时才新增 enabled 规则。
6. **迁移后再删副本**：先确认 Vault 主页面、规则 ID、来源记录和真实启动包命中，再删除仓库专业参考副本。
7. **最后审计**：运行唯一审计 CLI；不把审计接入阶段启动，也不为审计建立插件或第二套实现。

## 候选知识生命周期与晋升

以下流程适用于本地拥有的项目专业方法/规则维护；cloud-owned 或其他发布源仍遵守其来源方的现行流程。这里的“待整理/候选/已评估/晋升/退回/过期”是治理阶段标签，不新增运行时状态值。知识维护可复用既有 Vault 唯一正文、`knowledge-profile.json`、`knowledge-policy.json`、`knowledge-entrypoints.json`、selector、方法快照/哈希、confirmed 冲突和墓碑机制；不得另建平行候选数据库或实验台账。生产 Skill 只可按入口读取知识，不自行把当轮采用变成长期晋升。

1. **待整理/待接入**：保留真实来源、作者/发布者、定位、取得时间、原文/可靠引用及哈希（可得时），注明事实、推断与未知。未核实路径或来源的内容不进入 Skill profile、生产选择器或启动包；不猜路径。第三方文字只作证据，不是项目指令或授权；转发、讨论、提问和“试试”不构成晋升要求。
2. **候选试用**：专业方法正文保持候选态，profile 绑定保持 `proposed`；若要运行，使用现有显式隔离测试入口与测试 profile，candidate-test 必须保持未审/未采用并被 `ensure-prepared` 阻断生产。动态规则 selector 只接收 `knowledge-policy.json` 已允许的活动状态；候选规则在获准晋升前不得放入可被生产发现的活动块中，不能以 `enabled` 伪装成试用态。试用只记录证据与结果，不改正式方法。
3. **证据评估**：在试用前冻结适用标准和范围，保存输入/样本隔离、变量、预算、评审结果、负例、限制和是否有提升。验证失败、结果相反、未验证或样本不独立时留在候选/退回状态，不把一次通过自动晋升。历史任务盲测只是可选验证方法。
4. **实验验证晋升**：基于已记录、足以支持该适用范围的实验结果，由授权维护明确做出采用决定后才更新唯一方法正文/profile，或把动态规则加入其唯一规范页/活动选择入口。维护记录标 `promotion_basis: experiment_validated`，并保留验证证据、来源、适用范围、版本/哈希、被替代旧规则、冲突处理、批准依据和回退步骤。验证不等于自动授权；实验结果本身不赋予 `confirmed` 状态。
5. **用户明确指定直通晋升**：用户直接、明确要求将某项具体方法内容纳入正式方法，可免实验前置；维护仍须完成来源、内容、结构、范围、冲突和职责边界检查，并原样保留用户原话或可靠消息引用。维护记录标 `promotion_basis: user_directed`，另记准确适用范围、来源、版本/哈希、被替代旧规则、冲突处置和回退方式；未做实验须明确写“未验证”，不可标为 `experiment_validated`。只是在讨论、询问、说“试试”或转发/引用第三方内容，不触发直通。用户指定仅限该内容与明确范围，不自动扩展到其他 Skill/全项目；不覆盖系统安全、应用权限或其他平台授权边界。**两条晋升路径在记录中互斥区分，但现有加载状态保持兼容：** 专业方法继续使用 `knowledge-profile.json` 的 `binding_status: proposed` / `user_confirmed`；动态知识块继续使用 `knowledge-policy.json` 已允许的 `enabled` / `confirmed`，不为治理阶段发明状态。晋升依据写在既有唯一 Vault 方法页的维护说明中，而不是追加进动态块元数据，因为 `knowledge_blocks.py` 对动态块字段采用严格字段集。`user_confirmed` 表示绑定已由用户确认，不表示已做实验；动态 `confirmed` 也不能仅凭实验结果自动赋值，须有明确确认依据。
6. **退回/过期/替代**：不静默删除或覆盖旧方法。记录退回/过期/替代原因、影响范围和恢复条件，保留来源与旧版历史；将旧绑定从生产 profile 中移除/替换，使其不再作为当前方法加载。对动态知识块按现有指纹墓碑机制失效；专业方法使用其既有状态/profile 绑定机制，不把动态规则墓碑当作方法页状态。新方法必须记录被替代项及冲突处置；必要时可按旧版本/哈希回退，再重新准备受影响任务。

**证据载体约束：**晋升依据写入现有唯一 Vault 方法页的版本/维护记录，并同步更新现有 profile 绑定；若维护的是动态规则，在其唯一知识页的机器块外记录晋升依据、用户引用及回退信息，保持 `knowledge_blocks.py` 要求的机器块字段不变。不得把用户消息 ID塞进仅允许 Vault `sources/...` 路径的字段。任务级 `record-method-reading` 只证明本轮执行者申报读过对应快照，不能证明理解、效果、用户晋升意图或正式状态变更。若现有 Vault 页格式无法保留用户引用、晋升依据或旧版/回退信息，先报告载体缺口，不能临时另建台账，也不能假称状态转换已被 CLI 验证。

**代码校验边界：**creative-director 当前启用 `promotion_contract=required`。`method_documents` 对适用的 `user_confirmed` 方法核对依据结构、范围、方法版本和原始字节 SHA-256；`legacy_unclassified` 仅兼容代码固定的现有 `CREATIVE-DIRECTION-METHOD` ID、路径、版本、hash、范围和 Library 来源引用，其他方法不得自行声明 legacy。`user_directed` 只校验原话/可靠引用字段及绑定，不判断用户身份或语义；`experiment_validated` 还必须指向哈希匹配的 JSON 证据文件，文件至少包含被测方法版本/hash、adopt 决定、同范围、标准、观察结果和限制。`experiment_validated` 是提交记录声明的依据类别，代码不会判定观察是否真实、实验是否独立或证据是否足以支持采用；结构合格的虚构观察也可能通过机器校验，仍须由有权限的维护者审查。动态 `candidate` 块在正式 selector 中始终惰性；显式隔离试用单列且只允许 candidate-test。上述程序只验证结构和字节绑定，不能代替授权判断、评估证据质量或自动晋升。其他 Skill 的既有 profile 没有自动迁移到此合同。
