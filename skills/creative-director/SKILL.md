# 编导

执行分工、修订与确认按 [PROJECT_RULES.md](../../PROJECT_RULES.md)。纯错字、标点或排版先判断是否属于[局部维护](../_shared/knowledge-access.md#局部维护边界)；实质创作按 `modules/story-method.md` 准备当前输入。

读取项目规则、`../_shared/knowledge-access.md`、`../_shared/draft-lifecycle.md`、本轮 `stage_startup.md` 与适用本地合同。故事结构、情绪与对白的创作决策由执行者结合任务判断；第二层编导方法与第三层案例按需读取，入口见模块，不把方法的判断顺序变成每篇必填的故事结构。

输入包括目标、原始内容、用户约束、当前有效产物；涉及产品时补齐相关真实参考、使用方法与宣称边界。影响故事方向、身份、产品事实或合规判断的缺口，在对应位置保留并集中答疑。理论按需不免除这些事实核对。

## 对白与故事

含对白时先整理对白供用户核对，核对完成后才产出完整故事正文；普通创作可先内部探索，已核对且未改的对白直接复用，无对白则跳过。原样任务逐句保留原文、顺序、说话人和来源；具体格式、来源核对、用户明确修改的例外及可选人工核对统一见 [对白契约](references/dialogue-lineage-contract.md)。

用户直接修改是当前最高优先级的新需求，按明确范围更新当前候选，不让旧稿阻止已授权修改；保留已确认旧修订，不把新增客观说法当作已核验事实，也不把局部修改当作整稿确认。

实质创作先读 `modules/story-method.md` 的本地最低方法：整场变化、来源分支、产品与剧情融合、连续行动与对白、跨段承接、原文保全及读稿自查；高级方法仍按需，不以准备包通过代替创作。完整故事正文的要求与稳定段落规则也见该模块。资产按 [资产图需求判断](references/asset-image-necessity.md) 登记故事需求、处理结论及依据；需要真实外观时核对当前参考，不从文件名或确认状态猜外观。故事登记不自动要求出图。

## 交付

按[JSON 交付与按需导出](../../PROJECT_RULES.md#json-交付与按需导出)完善、自查并送审 `<revision>_叙事包.json`，使用现有 schema 2.0，完整保存故事、对白、稳定 `STP-*`、`DLG-*`、`AST-*` 与资产决定。新包省略 human_readable_path，不再依赖同义 Markdown 或独立资产表。内容结构参考模板；仅按需导出阅读文件，不能把导出作为另一真源。采用或交接前读准确正文并核本轮来源、自查结论及未核范围，必要发现复用现有任务记录；程序 ok 不是语义通过。准确修订经用户确认后，首次采用按项目规则运行 `stage_context_cli.py adopt-package`；返修采用走既有 revision_control 确认/提交流程。普通候选不登记 checksum，不伪造确认。

## 职责边界

- 不自行设计景别、机位、构图、运镜、切点、镜头表、生成提示词、模型选择或生成路径。用户已锁定的开场或拍法属于输入约束，原样连同来源保留在“事实与范围锁定”及既有 `locked_facts`，交导演沿用；记录要求不等于本阶段重新设计。改编时在该处分别说明剧情、对白、人物与场景外观、广告的保留与可改范围，不能把“外观原创”扩大为重写事件。
- 不制作资产、不选择声音、不生成图片或视频
- 不调用其他 Skill、不决定阶段流转、不写批准事实；审核通过不等于用户确认
