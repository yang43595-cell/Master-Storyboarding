# 导演稿后的可选本机白模

入口仍为 `python -B -m scripts.blender_previs_cli`，不新建工作台。默认不选白模，现有导演、分镜、视频流程不变。用户选择具体镜号后才执行；`storyboard-planner` 负责导演稿，`blender-previs` 实现空间参考，`storyboard-director` 消费参考并按需补图。各 Skill 不自动调用下一阶段。

## 先对齐导演稿

生产前按本 Skill 原入口 `prepare` / `ensure-prepared` 建立本轮受限输入，运行 `story_sources --shot-plan` 与 `--narrative ... --storyboard ...`。程序只检查来源/对白，不证明拍法正确；人工对照确认正文核对本镜的场景、站位、动作起止、镜头目的与机位运镜。正文与结构化数据不同就先修错配，不能靠白模补写导演决定。时长与切点继承已确认导演稿；未定焦距、厘米数及动作内部时刻记实现试验参数，可行性不足返回用户，不自行加秒、拆镜或改拍法。以下 AST、镜号、修订与竖屏像素为《消失的公主》的项目特定示例，实际使用换成本项目确认输入。

## 无人物空间基座只建并登记一次

同一场景复用固定房间、家具、道具占位与尺度的**无人物**空间基座；有有效版本就直接选用，没有时按已确认多视图建立并实测。人物与剧情状态不写入该基座。基座建造与登记不自动授权全片镜头预演。

```powershell
python -B -m scripts.blender_previs_cli register-scene --project <项目> --scene-id AST-BEDROOM --revision R01 --scene <已有房间.blend> --evidence <实测检查.json> --recipe <房间配方.json> --reference AST-BEDROOM@bedroom_master_45
```

`--reference` 可重复，登记实际使用的全部确认视图。源文件只读复制到 `05_分镜/预演/空间/AST-BEDROOM_R01/`；登记 `ART-PREVIS-SCENE-AST-BEDROOM-R01`，以 `previs.scene.AST-BEDROOM` 为唯一当前基座。空间实测通过与登记不是逐镜用户视觉确认。更新基座必须新修订，旧基座保留且其逐镜依赖失效。

同一场景的镜头使用同一个 `scene_artifact` 及 SHA256；卧室剧情跨场号仍可共用该房间。建筑、固定家具及比例不按镜号重建。镜头只调整人物状态、必要道具状态、摄影机与取景；不得保存回基础房间。已渲染且输入未变的白模直接复用，不为了接入重新渲染。

## 按镜号准备与本机布置

```powershell
python -B -m scripts.blender_previs_cli prepare-shot --project <项目> --shot-id S03-150 --revision R02 --scene-artifact ART-PREVIS-SCENE-AST-BEDROOM-R01
```

生成 `05_分镜/预演/输入/S03-150_R02/shot-input.json`，保留确认导演包 artifact/revision/path/SHA256、正文指纹、场景公共设定、原镜头全文、相邻状态及基座版本。白模修订独立于导演 R03，不改镜号。

新镜头据此人工填写现有 `blender-previs-recipe.schema.json` 的**本镜有效配方**：只放本镜 `camera.shots`，列齐本镜人物，用稳定人物占位 ID、标准本机人体模块、明确颜色、身高依据、起止及关键动作状态，坐姿优先 `chair_id`。逐镜配方使用从 0 秒开始的本镜局部时间：`start: 0`、`end` 与 `project.duration_seconds` 均为已确认镜长，人物动作与摄影机清单沿用同一局部时间；原导演时间与镜号保留在输入绑定中，不改变镜长或切点。配方中的 environment 不被下面入口重建；必要道具的逐镜位置、旋转、缩放写入摄影机清单的 `props`，对象须已在基座存在。

```powershell
python -B -m scripts.blender_previs_cli --blender <本机5.2.exe> stage-shot --project <项目> --input <shot-input.json> --recipe <本镜有效配方.json> --output-dir 05_分镜/预演/布置/S03-150_R02
python -B -m scripts.blender_previs_cli --blender <本机5.2.exe> shoot --scene <布置目录/previs.blend> --shots <含shots的本镜摄影机清单.json> --output-dir <新渲染目录>
python -B -m scripts.blender_previs_cli --blender <本机5.2.exe> verify --recipe <本镜有效配方.json> --scene <布置目录/previs.blend> --shots <同一摄影机清单.json> --output-dir <渲染目录>
```

`stage-shot` 打开同一无人物基座，复用 runner 创建本镜人物和 shoot 创建全部摄影机关键帧，另存逐镜副本；核对房间网格/位置与原文件 SHA256 不变。已有同名人物时报错，不能静默覆盖状态或删除基座人物来绕过。没有本机标准人体时报告缺失，不自动联网安装。输出目录必须为空。

`shoot` 的 time/position/look_at/lens 和中间停留逐点生效，旧 CUT 相机绑定仅在本进程解除。道具 `props` 临时覆盖在本镜结束后恢复，不能污染房间文件。只需静态参考时在清单设 `video: false`；所选镜头确需相机运动或粗路径/中途遮挡的时序参考，且属于本次授权范围时才设 true，固定机位也可适用。`build` 的静态及俯视配置明确 `preview_video: false`、`topdown.video: false`、`topdown.show_paths: false`；只有用户明确要路径辅助图才显示路径线。`stage-shot` 不渲染，`shoot` 不自动生成俯视图。

`verify --recipe` 必须传实际布置该镜人物的有效配方，不能传无人物房间配方；技术检查在本镜起止、关键状态及规定采样核对人物接触、比例和相机投影，不证明所有帧或全程遮挡。坐垫承托按实际臀腿蒙皮最低点及支撑点下方的表面核对，不用脚尖或骨盆骨骼代替臀部接触；实际图/视频仍须查看，精细表演以文字及确认素材为准。

已有完整整场人物时间线的旧白模，在准确绑定本镜与原时间轴状态后可直接 `shoot` 并传有效人物配方验收，镜头清单沿用旧白模的整场时间，不归零；不得再向它 `stage-shot` 同 ID 人物。需要新增人物状态时回到无人物空间基座制作新逐镜副本，保留旧白模，不删除其人物或修改房间。旧白模输入、渲染与真实检查仍有效时直接复用。

## 同源网页快速预览

逐镜布置后可以先导出无需逐帧渲染的浏览器预览，再根据反馈修改候选。AI 负责调度配方；Blender 计算同一份动作与取景；Three.js 负责显示和播放。入口仍为现有 CLI，查看复用已有资产网页，不另建工作台。

```powershell
python -B -m scripts.blender_previs_cli export-preview --project <项目> --stage-dir 05_分镜/预演/布置/S03-150_R02 --output-dir 05_分镜/预演/预览/S03-150_R02
```

`--stage-dir` 必须包含本版 `stage-shot` 保存的 `previs.blend`、`resolved.recipe.json`、`shot-input.json` 与 `stage_manifest.json`；文件指纹、导演镜号及当前基座绑定必须一致。旧布置缺少文件指纹时，在新目录重新 `stage-shot` 后才能导出网页预览，已有正式渲染/确认仍按原流程使用。

输出目录必须为空，且是项目 `05_分镜/预演/预览/` 下的单个目录，目录名用字母、数字、下划线、连字符或点。导出 `preview.glb`、`preview_manifest.json` 与日志；失败保留 `export_error.json` 说明真实原因。清单包含来源指纹、人物认领色、帧率、画幅和逐帧摄影机世界/投影矩阵；GLB 烘焙本镜实际骨骼/约束动作，包含本镜道具覆盖，不保存回源白模。

打开 `scripts/打开视觉资产库.cmd`，在“项目资产”选择已连接项目，再点“白模预览”。支持导演机位、自由观察、俯视、播放/暂停及时间轴倒拖，末尾停留；人物颜色保持认领用途，辅助路径默认关闭，只供查看。摄影机按项目画幅留黑，不按网页窗口重新计算取景。

网页只读派生文件，不登记成正式参考、不记录确认、不授权生成。修改配方后在新目录重新布置/导出；来源文件、导演或基座变化时，旧预览显示过期并停止提供模型。预览反馈后继续按需 `shoot` → `verify` → 实际查看 → 用户确认/交接。网页快速预览不能替代 Blender 接触检查、正式参考图/视频或用户视觉终审。

## 登记、用户确认与交接

登记说明 JSON 用下列字段，不放生图提示词：

```json
{
  "appearance_refs": ["AST-PRINCESS@outfit_f50ffae9_final", "AST-FAIRY@pet_three_views", "AST-BEDROOM@bedroom_master_45"],
  "actors": [{"proxy_id":"chr.princess.mini","asset_id":"AST-PRINCESS","display_color":"#238BCB","state":"本镜起幅坐在原坐垫上","scale_basis":"15cm为实现试验值；正文依据为掌心大小"}],
  "camera": {"director_contract":{"framing":"逐字取shot.camera.framing","movement":"逐字取shot.camera.movement","focus":"逐字取shot.camera.focus"},"position":[1.43,0.98,0.632],"resolution":[720,1280],"parameter_basis":"已通过空间参考；不改正文"},
  "target_state":"本镜起幅",
  "coverage":"静态起幅空间，不证明整镜运动/表演",
  "limitations":["不承担身份服装或精细动作"],
  "render_backend":"local Blender 5.2.1 LTS Cycles CPU",
  "technical_evidence":"实际通过的verify JSON或原样保留的隔离实测记录绝对路径",
  "files":[{"role":"main_image","path":"白模PNG绝对路径"},{"role":"shot_scene","path":"逐镜blend绝对路径"},{"role":"topdown","path":"俯视PNG绝对路径"}]
}
```

例中的数值只描述已通过 S03-150 的空间参考，不是其他镜头的模板机位。例中的公主输出为含清晰头部特写的确认人物 1×4，面部与服装由同一文件承担；下游最小参考选择统一按 [唯一面部来源](../../storyboard-director/references/image-continuity-hard-rules.md#唯一面部来源)，不把独立头照机械追加到交接。actors 必须列本镜实际在场的所有人物，颜色全片稳定且互异；无人场景/物件镜明确写 `actors: []`，不虚构人物，也不能借空数组省略本镜人物。登记前由执行者逐项核对确认正文、scene.space_rules.subject_positions（如有）、shot.take 与 camera，确认无在场或影响画内动作的人物；现有 v4 只提供正文/AST 引用，程序不推断在场人数，空数组通过仅表示结构合法，不证明没漏人；未完成这项来源核实前，不可发起用户确认或交接。填写真正的 AST/output ID。真实检查记录必须通过，不能写假 `ok` 或把 mock 当实际 Blender 渲染。新渲染须保留 recipe、shots、渲染清单、日志与 verify 记录；导入旧试验须保留其真实检查范围及未测项。

```powershell
python -B -m scripts.blender_previs_cli register-reference --project <项目> --input <shot-input.json> --spec <登记说明.json>
python -B -m scripts.blender_previs_cli confirm-reference --project <项目> --artifact-id ART-PREVIS-S03-150-R02 --approval-ref <真实用户消息引用> --user-quote <用户原话>
python -B -m scripts.blender_previs_cli handoff-reference --project <项目> --artifact-id ART-PREVIS-S03-150-R02 --output-dir 05_分镜/预演/交接/S03-150_R02
```

白模登记在 `05_分镜/预演/镜头/<镜号>_<修订>/white-reference.json`，先是 candidate；只有实际用户确认才 current/user_approved。确认 scope=artifact 只覆盖这份白模参考，镜号在参考本身与 `reference_shot_id` 标明，不冒充导演整稿确认。文件哈希、导演正文/包、房间版本和确认母图全部复核后才交接。候选、失效、被拒用母图或文件变更会阻塞该镜，不回退旧素材。

登记和交接前按[覆盖范围三项检查](../modules/previs-method.md#覆盖范围三项检查)核准确用途。`coverage` 写实际核过的空间范围、镜号/相位与职责，`limitations` 写未覆盖和不得承担的职责；局部两席验证不得写“完整机房空间通过”，全景规模核对不得写“四鞋可见通过”。现有 `register-reference` 检查字段与技术证据，但不会从图片自动判定这三项内容，不以命令成功当作完整镜头可用。失败整镜的局部技术诊断不因此进入活动生成参考；用户确认、生成授权仍各自独立。

交接目录包含 `reference-handoff.json`、准确顺序的白模和母图字节副本及 `参考职责.md`。默认携带已登记 `files` 中受支持的图片/视频（PNG、JPEG、WebP、MP4、MOV、WebM、MKV、AVI），保留原 role 与 SHA256，不把 .blend、JSON清单或技术证据冒充媒体。其他已登记格式不默认为包内媒体；有未支持文件时列出其 role 并将覆盖声明限定到实际携带内容，不能继承完整运动覆盖。只交付部分媒体时，可重复使用 `--media-role main_image --media-role end_image` 等，role 必须已登记；局部包会限定覆盖，完整源记录仍按准确 artifact_id 回源。选择媒体不修改批准范围，不新增渲染或上传授权。白模只管空间/构图/承托/相机路径；母图负责人物脸、服装、精灵与场景外观。交接不调用生图/视频、不授权额度、不自动确认成图。开启白模的本镜才消费该包，其他镜头不新增白模门禁。

## 已授权云执行的显式运行位置

默认不写 `runtime_location`，继续只接受原本机 `local Blender...` 来源。仅用户已明确授权本轮云执行时，在同一登记说明中写 `runtime_location: cloud`，并如实写 `render_backend`（例如 `cloud portable Blender 5.2.2 LTS Cycles CPU`）。这不是自动迁移、安装或额度授权。

云候选先对真实逐镜副本运行原生 `verify`。其报告必须带实际 `blender_version`（真实版本，不设未证实的 5.2 技术下限）、`scene_sha256` 与 `render_manifest_sha256`；`files` 除主图外列唯一 `shot_scene` 和 `render_manifest`（原 `shoot_manifest.json`）。登记会比较场景、清单及主图的真实字节，复制并保留证据；后续读取再核对，不以来源文字替代检查。旧本机参考不用补写或迁移。

运行位置和版本随白模参考及交接包保留。确认仍是独立步骤：云端技术通过只登记candidate，不自动user_approved，不绕过导演/正文/同基座/外观参考绑定、返工失效和具体用户确认。不得把云源伪标为本机，不把静态切点图登记成完整运镜已验证。

## 回滚与已确认文件

源试验目录原样保留，正式接入全部是字节复制。首次登记前将 artifact_manifest/project_state JSON/MD 备份到 `99_历史与废弃/白模接入前登记备份/`。暂停选用白模即可沿原流程；撤销采用时只把本次 `previs.*` 登记标失效并从当前 ID 列移除，保留原确认记录与文件。项目后续已有改动时不能拿整份旧登记备份覆盖当前状态；按本次新增的产物 ID 做局部撤销。代码用本次局部 diff 回退，不对脏工作区执行整文件 checkout/reset。


## 现有 GLB 空间的薄导入

JS 已导出静态 GLB 时，使用 Blender 原生 glTF 导入，不重建房间或另建人物动作真源：在空场景执行 `bpy.ops.import_scene.gltf(filepath=...)`，保存为新的无人物 `.blend`，再走上面的 `register-scene`。仅复制到新输出，不覆盖 GLB、旧基座或已确认文件。

导入前保留 GLB SHA256 和其来源/尺度依据；导入后检查米制单位、世界轴向、稳定对象 ID（含父子层级）、关键家具的世界包围盒与来源 manifest 尺度一致。座椅需要实际座面子网格，包围盒不能替代承托检测；逐镜人物只写 `stage-shot` 副本。导入证据注明无人物基座及实际检查范围，登记后两个或更多镜头复用同一 artifact/hash，核对基座字节不变。不得把 TEST 夹具确认为真实项目。

Blender 4.3.2 已实测原生 GLB → register-scene → 两镜 prepare/stage → export-preview；这不证明 5.2 `.blend` 向下兼容，也不证明 MPFB 已安装、正式 shoot 媒体通过或用户已确认。具体功能/文件格式失败只阻断对应分支。正式云参考仍要求原生 verify、同一逐镜场景/渲染清单/主图的字节证据，不能用粗模导出成功顶替。

### 确认重试与活动返工

`confirm-reference` 先复核生产模式、原始依赖、冻结与准确字节，再将收据、清单、当前选择与状态阅读副本写入现有可恢复事务。同一 artifact / checksum / 文件及确认引用、原话的重试返回同一收据；不同确认内容拒绝覆盖。中断后再次执行同一命令会恢复已有提交意图；没有提交意图时旧 current 与下游有效性保持。不得删除真实收据或用首次接入备份覆盖后续项目状态。

活动返工冻结的 logical_id 不可经 `confirm-reference` 提前采用，须走既有 revision_control 变更确认/提交流程，或由用户明确取消变更后再操作。候选登记与技术验收不解除冻结、不授权生成。
