# 导演：从故事到视听分镜

## 承上启下的职责

编导确定故事发生什么、人物关系、事件与对白；本 Skill 把已确认的故事设计成观众能够经历的情绪过程，决定这些内容怎样成为按顺序看到和听到的一段戏。按[逐场创作与确认](../../PROJECT_RULES.md#逐场创作与确认)逐段完善，最终主交付是完整的视听分镜稿：用户在进入视频 Skill 前，能够理解并审定整段拍法。

- 承接已确认叙事，保留事实、事件顺序、对白和说话者；在输入允许的创作范围内作出具体的镜头、表演和声画设计。发现需要改写故事或补充事实的问题时返回编导，不自行补写。
- 依照绑定方法，用“情境与表达目标 → 拍法选择 → 可读效果”说明创作决定。确定每场的重要情绪变化及其视听展开：谁受到影响、如何回应，观众此刻需要看谁、听到什么；再决定各镜头的观看对象、景别与构图、人物动作和反应、必要运镜与灯光、声音、切点和前后状态。交付可执行的选择，不把影响拍法的互斥选项留给下游决定。
- 说明节奏与停留的安排、时间依据及其不确定性；未测时长不冒充实测，不以镜头数量代替表达是否充分。按模块先写连贯的视听段落，再确认剪辑边界并逐镜展开，最后核对段落与表格的对应；不从表格空栏倒推拍法。
- 视频 Skill 承接用户审定的拍法，负责提示词、素材引用和生成分段。实现受限时返回具体镜头及影响，需改变导演决定的部分由本阶段形成修订并重新送审，不能由下游暗改。

本阶段同时验收“拍法可执行”和“重要情绪有视听表达”：整段拍法已经清楚，关键情绪与关系转折能从实际画面、表演和声音中读到，可供用户审定并被下游忠实实现。叙事与对白覆盖完整不等于表达充分。表格完整、引用正确与镜头数量只是辅助检查；本阶段不承诺模型生成效果，也不要求先制作全套分镜图。逐镜复刻须以原片证据核对；只依据故事创作的拍法明确标为候选导演设计。

由当前执行者按 [PROJECT_RULES.md 的 Skill 执行分工](../../PROJECT_RULES.md#skill-执行分工) 执行本阶段；默认由主 agent 直接执行和自检，已明确委派时由受派执行者完成。

纯错字、标点或排版维护先按 [共享局部维护边界](../_shared/knowledge-access.md#局部维护边界) 判断；符合时只做局部检查，下述整阶段准备适用于实质创作与修改。

先读取 `PROJECT_RULES.md`、`../_shared/draft-lifecycle.md` 等共享红线和 `modules/shot-planning.md`。按模块先建立准备包，再读取当前 `stage_startup.md`、`references/专业影视分镜执行规范.md` 和 `../creative-director/references/dialogue-lineage-contract.md`。本 Skill 的已确认专业判断由 `knowledge-profile.json` 绑定，并随 `prepare` 写入本轮完整方法快照；完整阅读后登记读取证据，再完成产出前校验。已迁移方法不从旧本地副本重复读取；当前知识包中适用的补充条目仍按共享知识入口核对，不因主题相近整块排除。灯光判断以该快照中的导演规划方法为准，不再读取旧灯光参考的导演预演段落。交付使用 `templates/专业影视分镜输出模板.md` 与 `../../schemas/storyboard-package.schema.json`；提交候选前读取 `references/专业影视分镜审查门槛.md`。

输出采用模板中的通用紧凑排版：场景共用设定写一次，逐镜保留六项决定；情绪推进与删除测试用于创作自检，不强制输出独立 Beat、Panel 或删除测试表。

## 输入门禁

- 只消费 `project_state.json` 与 artifact manifest 指向的已确认 `narrative.package` revision；确认状态、路径或 revision 不一致时停止。
- 完整阅读已确认编导 Markdown（长文按自然章节连续读完），故事与对白原文只读这一份。对准确登记的叙事包 2.0 运行 `python -m scripts.core.story_sources --project <项目> --narrative <叙事包> --reading-supplement`，程序先完整核对两份内容，再返回除重复原文以外的全部结构化字段；完整读取该补充视图中的锁定事实、STP/DLG/AST 引用、资产约束、状态、来源和未决项。校验失败先处理具体差异，不靠只读其中一份绕过；视图不另存为交付包，不证明用户确认。旧格式沿原兼容入口，不用本选项跳过原文。不得新增、删除、改写或重新编号上游事实；对白文本和说话者必须逐字沿用。当前上下文已无必要原文时补读原文，不能只靠阅读记录或补充视图创作。
- 资产输入同时读取项目规则指定的现行资产需求调整记录与当前资产表；原叙事事实保留，用户已确认的新增需求按核对位置引用，取消资产图不等于删除故事物件。导演不自行新增需求。
- 本段需要引用资产图时，先用 AST 与明确 output ID 查询当前段范围；只在首次用途、版本或所需视觉判断变化时定向查看图片。确认登记和文件存在不等于已看懂画面。
- 缺少会改变剧情、人物、空间或资产事实的信息时，只返回带来源段落和受影响镜头的缺口，不自行补写。

## 交付合同

交付顺序与答疑位置以 [项目规则：双文件产物串行交付](../../PROJECT_RULES.md#双文件产物串行交付) 为唯一流程正文。本 Skill 的模板只规定稿件结构，不能替代对话中的答疑或用户审稿。

最终每个已确认修订交付：

1. `<revision>_导演镜头方案.md`：完整视听分镜稿，按播放顺序呈现整场与逐镜拍法，作为用户创意审定的主要对象；沿用现有文件名。
2. `<revision>_storyboard-package.json`：符合 `storyboard-package.schema.json` 的 v4 结构化合同，只引用叙事包和其稳定 ID。

两份文件分别登记到 artifact manifest，并引用已确认叙事包的 `artifact_id` 与 revision。`storyboard-package-v1.schema.json`、`storyboard-package-v2.schema.json` 与 `storyboard-package-v3.schema.json` 仅用于旧项目的只读兼容，不得据此新建或修改生产产物。

## 硬禁区

- 不新增或修改资产需求，不制作、移动或确认资产。
- 资产引用只用 `04_资产/当前资产清单.json` 里的有效编号：已取消出图的物件可以保留为故事事实，但素材与出图引用不得用它，物件写在镜内过程；已拆分的改用子项。提交候选前用 `story_sources --shot-plan` 自查。
- 不调用 Blender，不设计 Blender 配方或预演执行。
- 不决定视频模型、生成分段、时长上限、提示词、生成参数或正式分镜图。
- 不修改剧情、角色、事件顺序、对白、产品事实或叙事包 ID。
- 不调用下一 Skill、不决定阶段流转、不写批准事实。

结构化后运行 `python -m scripts.core.story_sources --project <项目> --narrative <叙事包> --storyboard <导演包>`，验证版本、原文与段落覆盖。STP 只是原文定位，不是镜头数量或事件摘要；一段可对应多个镜头，同一镜也可引用多个连续段落。
