# 导演：从故事到视听分镜

## 承上启下的职责

编导确定故事发生什么、人物关系、事件与对白；本 Skill 把已确认的故事设计成观众能够经历的情绪过程，决定这些内容怎样成为按顺序看到和听到的一段戏。按[逐场创作与确认](../../PROJECT_RULES.md#逐场创作与确认)逐段完善，最终主交付是完整的视听分镜稿：用户在进入视频 Skill 前，能够理解并审定整段拍法。

- 承接已确认叙事，保留事实、事件顺序、对白和说话者；在输入允许的创作范围内作出具体的镜头、表演和声画设计。发现需要改写故事或补充事实的问题时返回编导，不自行补写。
- 实质创作先按 [镜头规划加载与合同入口](modules/shot-planning.md#从整场意图想出画面) 完整阅读三份本地基础参考，再读 [画面构思与拍法选择](references/visual-conception.md)：从整场关系变化、观众体验和可见载体想出观看路线，在重要岔路比较后选定，再落到镜头；不逐句配镜。创作后分别检查表达质量与执行连续性。
- 依照绑定方法，以“情境与表达目标 → 拍法选择 → 可读效果”形成整段视听设计；按模块先写连贯视听展开，再定剪辑边界和逐镜拍法。不从表格空栏倒推创作，也不把互斥选项留给下游。
- 说明节奏、停留、时间依据与未验证限制；守住用户时长及制作预算，未测不冒充实测，不以镜头数量替代表达判断。
- 视频 Skill 承接用户审定的拍法，负责提示词、素材引用和生成分段。实现受限时返回具体镜头及影响，需改变导演决定的部分由本阶段形成修订并重新送审，不能由下游暗改。

本阶段同时验收“拍法可执行”和“重要情绪有视听表达”：整段拍法已经清楚，关键情绪与关系转折能从实际画面、表演和声音中读到，可供用户审定并被下游忠实实现。叙事与对白覆盖完整不等于表达充分。表格完整、引用正确与镜头数量只是辅助检查；本阶段不承诺模型生成效果，也不要求先制作全套分镜图。逐镜复刻须以原片证据核对；只依据故事创作的拍法明确标为候选导演设计。

由当前执行者按 [PROJECT_RULES.md 的 Skill 执行分工](../../PROJECT_RULES.md#skill-执行分工) 执行本阶段；默认由主 agent 直接执行和自检，已明确委派时由受派执行者完成。

纯错字、标点或排版维护先按 [共享局部维护边界](../_shared/knowledge-access.md#局部维护边界) 判断；符合时只做局部检查，下述整阶段准备适用于实质创作与修改。

读取 `PROJECT_RULES.md`、`../_shared/draft-lifecycle.md` 等共享红线后，按 `modules/shot-planning.md` 的唯一入口完成准备、完整方法阅读、适用本地合同与产前校验；有效阅读按共享规则复用。补充资料按当前表达或事实缺口，从准确候选路径定向读取；方法的出处链接不自动成为额外全文必读，也不因主题相近排除适用补充。灯光沿用方法快照，不重读旧导演预演段落。交付使用 `templates/专业影视分镜输出模板.md` 与 `../../schemas/storyboard-package.schema.json`；自查按 `references/专业影视分镜审查门槛.md`。

本阶段适用的本地合同：[专业影视分镜执行规范](references/专业影视分镜执行规范.md)与[对白来源合同](../creative-director/references/dialogue-lineage-contract.md)，按上述唯一准备入口读取与核验。

输出采用模板中的通用紧凑排版：场景共用设定写一次，逐镜保留六项决定；情绪推进与删除测试用于创作自检，不强制输出独立 Beat、Panel 或删除测试表。

## 输入门禁

- 只消费 `project_state.json` 与 artifact manifest 指向的已确认 `narrative.package` revision；确认状态、路径或 revision 不一致时停止。
- 分清事实与拍法的确认范围：用户明确锁定的拍法、已确认导演版本或片段均按准确来源保留；当前授权修改时另作候选并重新送审。AI 自选但未经用户确认的旧拍法不因进入旧稿、任务摘要或已确认叙事而自动锁定，可在本轮创作范围内重选。来源不明且会改变拍法时先核对确认记录，仍不明确再问；不擅自解锁。局部换服等修改只处理相关镜头及直接连续性，不扩大为全量重设计。
- 完整阅读已确认叙事 JSON 的故事、对白、锁定事实、STP/DLG/AST、资产约束、来源和未决项；新包运行 `python -m scripts.core.story_sources --project <项目> --narrative <叙事包>` 核对原文及引用，不再同时读取同义 Markdown 或省略原文的第二份视图。历史带 human_readable_path 的包仍完整阅读原稿并用 `--reading-supplement` 核对双文件一致性；校验失败处理具体差异，不删除旧字段绕过。对白文本和说话者必须逐字沿用，不能新增、删除、改写或重新编号上游事实。上下文中缺必要原文时补读，阅读记录不能代替原文。
- 资产输入同时读取项目规则指定的现行资产需求调整记录与当前资产表；原叙事事实保留，用户已确认的新增需求按核对位置引用，取消资产图不等于删除故事物件。导演不自行新增需求。
- 本段需要引用资产图时，先用 AST 与明确 output ID 查询当前段范围；只在首次用途、版本或所需视觉判断变化时定向查看图片。确认登记和文件存在不等于已看懂画面。
- 缺少会改变剧情、人物、空间或资产事实的信息时，只返回带来源段落和受影响镜头的缺口，不自行补写。

## 交付合同

交付顺序按[JSON 交付与按需导出](../../PROJECT_RULES.md#json-交付与按需导出)。完善、自查并送审 `<revision>_storyboard-package.json`（v4），保存完整视听展开、场景、逐镜拍法、对白承载、时间依据与衔接，只引用已确认叙事修订及稳定 ID。新包省略 human_readable_path，不要求同义导演 Markdown。正常顺序为候选 JSON → 自查校验 → 现有审核网页审查 → 用户确认准确 JSON 版本及范围；网页按项目根规则使用既有入口，不虚构 URL，离线校验不代表已发布。仅用户明确要求 Markdown 检查稿时才从同一 JSON 版本导出，不作为前置、不新建业务权威、不反向覆盖 JSON、不登记为业务依赖。用户确认准确修订后才登记采用，正式交接仍须相应确认及明确继续授权。`storyboard-package-v1.schema.json`、`storyboard-package-v2.schema.json` 与 `storyboard-package-v3.schema.json` 仅用于旧项目的只读兼容。

## 硬禁区

- 不新增或修改资产需求，不制作、移动或确认资产。
- 资产引用只用 `04_资产/当前资产清单.json` 里的有效编号：已取消出图的物件可以保留为故事事实，但素材与出图引用不得用它，物件写在镜内过程；已拆分的改用子项。提交候选前用 `story_sources --shot-plan` 自查。
- 不调用 Blender，不设计 Blender 配方或预演执行。
- 不决定视频模型、生成分段、时长上限、提示词、生成参数或正式分镜图。
- 不修改剧情、角色、事件顺序、对白、产品事实或叙事包 ID。
- 不调用下一 Skill、不决定阶段流转、不写批准事实。

结构化后运行 `python -m scripts.core.story_sources --project <项目> --narrative <叙事包> --storyboard <导演包>`，验证版本、原文与段落覆盖。STP 只是原文定位，不是镜头数量或事件摘要；一段可对应多个镜头，同一镜也可引用多个连续段落。
