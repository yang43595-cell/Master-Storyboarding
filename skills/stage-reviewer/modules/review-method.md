# 独立审核方法

仅在用户明确要求独立审核时使用。默认由当前对话自查、直接修改，不创建审核 agent，不交接生产对话，也不生成审核包。

独立审核只读当前候选、用户指定的来源范围和目标 Skill 的冻结清单。合同检查与产物检查分别引用 `review-profile.json` 中的两类清单；不凭文件存在、哈希或历史结论推定质量通过。

确认本轮范围与来源后，导演稿先按播放顺序读候选的整段视听展开，再核对作者的取舍说明及逐镜字段；先判断重要变化如何被体验，不从“有反应／有用途／引用正确”倒推表达通过。结论先简述关键判断及未验证范围，再列发现；只核既定方法，不新增每镜双案、镜头配额或固定时长要求。资产、平台与实片各按实际读取的证据范围下结论，草稿保存、引用连通和未生成记录不能代替实际像素、声音或成片验证。

每项发现只写：`check_id`、`target`（具体对象）、`evidence`（可复现证据）、`impact`（实际影响）。证据不足写“无法确认”，不猜测。结论仅为“通过”“有条件通过”“不通过”；有条件通过须列出待用户接受的限制。

## 视频提示词的直接审核分支

仅用户明确要求视频提示词独立审核时适用。直接交当前候选的准确路径、修订与哈希、来源导演及对白、实际素材和用户指定范围，读取适用规范与目标 Skill 对应清单；复审补充实际修改与未决发现。沿现有文档或对话记录结果，不新建 task_basis、review_packet、review_scope 或调用退役的视频 prepare/review-pack。以下包化与正式留档命令只用于仍采用准备包的其他阶段，不借本分支省略来源核对或升级确认。

## 默认轻复审

返修回原审核者，只复核修改段、上轮未决发现及其直接影响，不重新传完整聊天或已解决历史。除非用户要求正式留档，不保留编号水位、基线快照、生产者回复、审核谱系或上下文检查点。

`review-pack` 默认只维护当前 `review_packet.md` 和 `review_scope.json`，范围文件保存当前候选/来源及冻结验收的实质身份，不建立版本目录。发现可以直接在对话回报；若使用 CLI 复审，把上述四项发现保存在同一 JSON 的 `issues` 数组，传 `--review-mode revision --previous-review <该文件>`，不要求 `review.json`/`review.md` 双份报告。

候选字节变化时，追加 `--change-summary "位置：实际修改；直接影响"`，可重复。它是执行者声明，程序没有旧正文时不假称已实算 diff；审核者仍核对当前正文和准确来源。候选路径或任务/验收实质范围变化须明确后重新首审，不能拿旧范围暗中扩审。无论是否改变候选，每条输入未决发现都须回应；已解决项保留原 `check_id`、`target`，提供解决证据和影响，并标记 `status: resolved`；遗漏不等于已解决。只有当前未决对象可以关闭，不得用 suggestion 降级清除未决；同一检查项的多个发现须把 target 精确到不同问题位置，禁止重复键互相覆盖。其余发现不写状态即仍待复核。

当前磁盘 `review_scope.json` 是候选版本与未决义务的唯一机器依据。发现记录可以不复制 scope，此时视为对当前包的答复；若携带 scope，必须与当前候选、直接证据和未决集合一致。旧 scope 只能用于核对，不能替换当前状态；不得重放旧报告冒充本轮答复。

方法阅读缓存与审核身份分开：history、无关历史登记、manifest 时间戳不改变实质验收；任务依据内的实际来源版本、当前选择、范围、方法或冻结清单变化须重新准备并明确适用审查范围。通过 --evidence 追加的直接来源只在 scope/delta 中记录新增、撤回及换版的前后身份；原审核者据内容判断相关未决或既有通过项是保留、重开或无法判断，不以哈希变化自动要求全量首审，也不能用已撤回或过期证据关闭问题。缓存命中不是当前上下文仍保留原文或当前执行已获授权的证明。

## 用户明确要求正式留档时

使用 `--formal-archive`。首审输出 `review_rounds/<内容指纹>/` 中的包与范围；`review.json` 保留真实 `reviewer_id`、原样的 `scope` 和 `issues`。每个问题包括 `id`（如 `B-001`）、`check_id`、`status`（resolved / unresolved / new-blocker / suggestion）、`target`、`evidence`、`impact`。

正式复审传 `--previous-review`、与上轮产物顺序相同的 `--baseline`、`--producer-response`。回复可内联 JSON：`{"responses":[{"id":"B-001","summary":"实际修改或未修原因","evidence":"位置"}]}`。每个未决 ID 都须回应；基线须与上轮哈希一致，程序从相同字节计算 diff 并核验当前版本。冻结范围、真实审核者和未决 ID 不得丢失。基线只供准确差异和旧位置追溯，不是默认全文阅读清单。

旧完整调用仍兼容，显式提供基线/生产者回复即沿用正式模式；缺一项不得降级成轻审核。旧记录只有整个任务文件哈希时，继续严格按旧哈希比对，不补造历史实质身份。新记录另存实质任务身份，文件哈希仅追溯，不把可再生阅读缓存元数据当作验收标准。已解决正文不重复交接，历史记录不批量改写。

两种模式都只记录审核事实，不授予生产、付费、发布、下一阶段执行或用户确认。
