## 问题与修正留档

项目遇到可复现、可能反复发生或影响出片的问题时，执行者在本轮收尾前主动留档。已授权的修复、优化和规则调整随改动一起记录，无需单独请用户确认。留档只描述本轮处理和证据，专业方法晋升或扩大改动范围仍按原授权。仅影响单个业务项目的故障或返修记在该项目现有任务或回执文件里，交接时给出准确路径。涉及仓库共同流程、校验、跨阶段交接、历史兼容或取舍的决定记在本文件。普通错字、排版和能从差异直接看明白的小修沿用现有任务记录或 Git 提交说明。

动到已有行为前，以待改文件名、入口、函数名、字段或具体报错在本文件定向检索。业务项目续作时同时查该项目现有任务记录或回执。只读相关条目，核对现行规则、代码和测试。查不到时，沿目标文件的 Git 历史核对已有依据。若新方案与旧决定冲突，先查原问题是否还存在，再说明要保留、替换或废止什么。新的决定链接旧条目，旧条目追加状态注并指向新的现行出处。

### 记法约定

- **背景与原因**：具体症状、触发条件和已证实的根因。未查明时注明待核。
- **决定与边界**：采用的做法、原因、影响范围，以及必须保留的检查或兼容行为。若否掉了容易被重新提出的方案，简记后果。
- **验证与依据**：写实际复现或回归结果，以及当前规则、代码、测试、任务或提交的准确定位。未实施或未验证的部分如实标注，后续有结果再补。

同一问题沿已有条目补充，正文写上可用于后续检索的文件名及准确入口、函数或字段。现行规则仍写在原规则文档，这里只留背景、取舍和证据。交接只带相关条目的链接和本轮差异。发布或提交对应改动时，记录随改动进入同一分支或工作树，供新会话查阅。

依据引用的文件若日后佚失，就地把链接降为纯文字并标注「原记录已佚」与核对日期，保留原文件名，不猜测、不改指其他文件。

决定被后续规则或实践取代时，不改写原条目，只在条目末尾追加一条「现行状态注（日期）」，写明哪部分已被取代、现行出处在哪；未被注明的部分继续有效。

### 视频提示词的时长只记制作参数（2026-11-19）

- **定位**：`video-script-template.md`、`video-method.md`、`generation_boundaries.py`、`canvas_readback.py`、`prompt_body.py`、`validate_shot_durations`、`shot_durations`、`parameters.duration`。
- **背景与原因**：旧模板把逐镜时长同时写进正文和制作参数。正文解析会漏掉带镜头标题的区间，混用写法也可能误拦。样例复现了这两种情况，《罗盘剧情》抽查的 45 段正式正文未发现逐镜秒数区间。
- **决定与边界**：新稿用动作或对白交代切镜，逐镜时长和总时长只记制作参数。采用、分段和画布不解析正文秒数来决定通过与否。保留逐镜合计校验及明确要求在画面上叠加字幕或时间码的检查。恢复正文时间校验会重新维护两套时间。
- **验证与依据**：复查确认旧稿混合区间和对白里的「2–3 秒」可通过，参数加总错误和画面叠加时间码仍被拒绝。定向回归 478 项通过、另有 11 个子测试通过。全仓首轮的两条旧断言 `timeline_gap` / `timeline_end` 在工作树同步切换时仍期待正文秒数拦截，稳定后复跑通过。见[视频模板](../skills/voiceover-to-video-script/templates/video-script-template.md)、[分段检查回归](../scripts/tests/test_generation_boundaries.py)和[画布回归](../scripts/tests/test_workflow_repair_cli.py)。

### 隔离运行依赖只能由当前解释器持有（2026-09-21）

- **背景**：仓库同时被两个解释器使用——项目 Python 3.13（测试与确定性工具）和 Codex 内置 Python 3.12（视觉资产库服务）。

### 用户确认范围只有一个判定权威（2026-09-21）

### 子 Agent 的委派边界写进规则（2026-09-21）

- **背景**：本项目先试过"主 agent 编排 + 生产子 agent + 空白审查子 agent"的多 agent 形态，实际 token 消耗极大且难以优化，改成单 agent 直接执行。审查一份外部架构说明书（单一主 Agent 与确定性执行引擎）后确认：那份文档同样把多 Agent 列为可选扩展，并把"用多个 Agent 代替任务调度器"写成反模式——真正省下成本的是"确定性步骤不再过一遍语言模型"，不是"agent 变少"。
- **决定**：`PROJECT_RULES.md` 的 Skill 执行分工补两条边界：① 只有只读检索整理、隔离组件开发、独立检查三类可派；目标解释、整体创意方向、同一份核心稿并发改写、费用与账户授权、最终验收不得派，子 agent 产物由当前执行者审阅后写入项目真源；② 确定性步骤优先脚本或现有 CLI，不把子 agent 当调度器，出现真实瓶颈才加。（注：该节后已迁至 docs/rules/execution.md「Skill 执行分工」。）
- **为什么**：把"该不该派"变成可核对的清单，以后不必每次重新讨论"要不要派个 agent 审查"；同时把"确定性步骤不套模型"写成规则，保住单 agent 架构已省下的成本。
- **放弃的方案**：① 只保留原来"默认不新建空白审核 agent"一句——没说清哪几类不能派，遇到分叉仍要反复判断；② 照搬外部说明书的 Brief/Treatment/Source/Run 目录结构——职责我们已有对应物（叙事包、产物清单、确认记录、素材清单），搬过来只多一层要同步的文件。
- **依据**：`docs/rules/execution.md`（Skill 执行分工）；外部架构说明书《单一主 Agent 与确定性执行引擎架构》。本次只改规则文本，未改任何执行脚本。
- **现行状态注（2026-11-09）**：背景中"改成单 agent 直接执行"是当时的阶段表述，其后执行分工又有演进（创作轮改由全新、专属的生产 agent 执行、图片生产按批次委派），现行正文以 [执行分工](rules/execution.md#skill-执行分工) 为准。本条决定的委派边界（可派范围与不得委派项、确定性步骤优先脚本/CLI）仍被现行正文继承，继续有效。

### 资产图生成不设额度门禁（2026-09-21）

- **背景**：审查发现 `record_paid_approval`、`paid_action_id` 与 `guard_action(paid_action_id=...)` 全仓没有生产调用方（只剩测试），"授权额度 remaining"写好了没人查。接上它需要把每次资产图生成挂进变更案，而资产网页按现行规则与导演规划并行。
- **决定**：不接。资产图生成的费用门槛继续由"用户在资产网页点授权生成"承担，每步仍落 `authorization` 回执；变更案的 paid_approvals 机制保留不删，只服务将来确实需要预算门禁的项目。代码里就近写明原因，避免下次审查又当成缺陷。
- **为什么**：把并行流程卡成串行，代价大于收益；现行的"人工点授权 + 逐步回执"已经覆盖实际风险。
- **放弃的方案**：① 强制资产生成挂变更案并核对 remaining——打断资产与导演规划的并行；② 删掉 paid_approvals 相关代码——删一个已有测试的机制，日后真要做预算门禁还得重写。
- **依据**：用户 2026-09-21 裁定“不用拦”。
- **现行状态（2026-11-17）**：清理未接入生产的变更案付费额度接口。保留已有记录、变更案冻结检查及各生成入口的实际授权检查。
