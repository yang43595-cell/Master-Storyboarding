# 技术决策记录

> 我和未来的 Claude 之间，靠这份文档对齐"**我们当初为什么这么定**"。每一次重启我都是全新会话，短期记忆清零；只有落在这份文档里的理由才跨会话活着。
>
> 这份是**决策记录，不是更新日志**：git 已经把"改了啥"记得很清楚了，这里只补 git 补不上的部分——"为什么这么定 + 否掉了什么"。读了它，未来的我才不会把当年删掉的东西又加回来、把否掉的方案重新发明一遍。
>
> **改动 / 加东西前，和 [PROJECT_BLUEPRINT.md](PROJECT_BLUEPRINT.md) 一起读一遍这里。**

## 记法约定

每条按下面的格式，**随做随记**——每做一个非显然的技术决定就补一条，你点头后存档：

- **背景**：当时是什么情况 / 撞了什么坑
- **决定**：最后选了哪条路
- **为什么**：选它的理由
- **放弃的方案**：没选哪条、为什么放弃——**这条最关键**，它才是真正防止未来走回头路的东西
- **依据**：git commit SHA 或文档出处，方便你核实

**别写"改了啥"**（那是 changelog，git 会说）；**写"为什么 + 否掉了什么"**。一条宁短勿滥，凑不下就拆两条。

## 已沉淀的决策

### Three.js 只播放 Blender 同源白模（2026-10-03）

- **背景**：白模已有 Blender 调度和检查能力，但修改后逐帧渲染才能查看，反馈较慢；用户选择“AI 调度，你看预览”。
- **决定**：复用逐镜布置与拍摄准备逻辑，导出烘焙动作 GLB 和逐帧相机世界/投影矩阵，用已有资产网页中的只读 Three.js 预览显示；依赖本地固定 0.180.0（MIT）。
- **为什么**：实际坐姿、骨骼动作、道具覆盖、跟随和变焦共用 Blender 的求值结果，网页拖动时间轴仍与正式拍摄取景一致，且无需每帧渲染。
- **放弃的方案**：不在 Three.js 重建房间或重写动作求解；不加入手工拖动编辑器与第二份调度真源，避免预览与正式结果漂移及维护负担。
- **依据**：本轮用户确认的实施计划；[项目入口](../skills/blender-previs/references/项目接入.md#同源网页快速预览)、[本地依赖来源](../scripts/visual_asset_ui/vendor/three/NOTICE.md)；隔离 Blender/浏览器验证脚本 `blender_preview_check.py`、`three_preview_check.mjs`、`three_preview_ui_check.mjs`。

### Web 资产资料入口与实际阅读分开（2026-09-12）

- **背景**：资产 Web 在模型读取前执行 ensure-prepared；专业方法绑定后会要求尚未发生的阅读声明，且旧资料包没有包含独立方法全文。隔离复现见 [第三批实施记录](development/third-batch-assets.md)。
- **决定**：沿用现有 library_runtime 作为 Web 受限读取入口，复用项目方法解析与动态选择器，完整送达适用正文后仍以一次模型调用完成写词、自查和修正。普通对话与视觉补充保留原阅读门槛；Web 工作记录只写本次请求目录。
- **为什么**：文件组装能证明资料完整，不能证明模型已读。两类事实分开后，方法可以迁移且保持单一正文，不必为了让程序通过而伪造执行者声明。
- **放弃的方案**：Web 复制一套旧 Skill、跳过全局校验的开关、自动登记 agent 阅读、恢复额外预读模型调用；这些做法分别造成方法分叉、门槛失真或无必要的调用增加。
- **依据**：`library_runtime.py`、`modules/web-input-contract.md`、`test_visual_asset_reading.py` 及配套 Vault 图片资产方法；本轮用户授权第三批架构调整，运行中网页尚未切换。

### Skill 由子 agent 执行，主 agent 持续协调（2026-09-09）

- **当日补充纠正**：用户明确要求打回必须回原生产子 agent，复审回原审核子 agent，包括下游打回上游及确认后另存修订。删除“优先复用”和“不可用自动换空白”的退路：用原标识继续／恢复，确实无法恢复时报告并暂停，未经用户授权不换执行者。空白创建仅用于尚未执行的新阶段首次生产／审核，以及用户明确授权的替换或独立新审；自动生成的包与流程图同步区分首次和返修。

- **背景**：用户多次要求 Skill 使用子 agent；任务 `01a0816c-b625-7973-bdd3-be3fb364a26f` 仍由主 agent 处理生产，交接时又要求用户另建任务。根规则缺少执行分工，蓝图只明确审核委派，启动与交接生成器仍输出含糊的“新生产对话”。主目录未提交修改也不会自动进入其他 worktree。
- **决定**：分工唯一正文放在 `PROJECT_RULES.md`，9 个 Skill 入口引用；生产、审核、已授权维护均由子 agent 执行。主 agent 负责上下文准备、派发、核对回报与用户交付。跨阶段使用原生空白子 agent，用户无需重开侧栏任务。同步本次修改到主目录和链接任务的执行副本时只应用相关差异，保留既有改动。
- **为什么**：执行者和“空白”的含义必须在规则、Skill 与实际生成的包中一致；修了一个工作副本不等于其他任务已读到修复。
- **放弃的方案**：只作口头承诺、只给审核派子 agent、让用户反复新建任务；不添加项目调度引擎或执行回执体系。文件校验不能证明宿主实际派发，运行情况以真实工具调用和回报为准。
- **依据**：本次用户要求；上述任务记录；`PROJECT_RULES.md`“Skill 执行分工”与 `scripts/stage_context_cli.py`。

### D-01 方向定调：个人轻量，只留拍片之路

- **背景**：项目原本叠了不少工程化 / 商业化脚手架：多个 schema、死脚本、`scene_topology` 引擎、29 个冗余测试、空 `references` 硬挂、9 篇治理文档。
- **决定**：定调为"**一个人做 AI 短剧的工具**"，只保留拍片这条路。不为了维护工具本身而加工程性重量（冗余格式合同、大型测试套件、治理审核规范、多 agent 运行时等）；默认选**更轻、更少**的路；已精简掉的东西**不重新引入**，除非它直接挡着你出片。
- **为什么**：这台工具只有你一个用户，你的手感就是标准；工具本身不值得我们投入防回归、可维护、通用这些工程投入。
- **放弃的方案**：做成通用平台 / 框架；补齐被删的 schema 与脚手架；扩成大型测试套件；加治理制度。
- **依据**：[PROJECT_RULES.md](../PROJECT_RULES.md)「方向」段、[PROJECT_BLUEPRINT.md](PROJECT_BLUEPRINT.md) §三/§五；commit `6559f18`、`768e3ca`、`a062f84`。**今后凡是想加工程 / 治理类东西，先回到这一个判断。**

### D-02 单一正文规则 + 薄指针入口

- **背景**：规则曾分散在 `AGENTS.md`、`CLAUDE.md` 正文里，蓝图也重复列过红线，几处同步极易漂移。
- **决定**：`PROJECT_RULES.md` 是**唯一规则正文**；`AGENTS.md` / `CLAUDE.md` 只做**薄指针**指向它；红线详情下沉到 `skills/_shared/`；蓝图不重复红线，只指向 `PROJECT_RULES.md`。
- **为什么**：避免同一规则多处维护导致漂移——多条文档同步是这套流程里最常出错的高频点。
- **放弃的方案**：在各入口各自维护一份规则正文。
- **依据**：commit `1f11fde`（薄指针）、`768e3ca`、`18ffbdc`。

### D-03 archive 引擎已删，历史由 Git 承担，勿引入"archived"状态

- **背景**：曾有 `core/archive.py` + `scene_topology` 引擎 + 一套"已归档 / 已确认"状态；后来把 archive 引擎删了。
- **决定**：archive 引擎删除后，**不再保留 "archived" 状态字段**；任何"历史上某个版本的产物"都交给 **git** 承担，不在运行状态里自造一个"已归档"。状态一律归 `project_state` 管。
- **为什么**：没有归档引擎时，"archived" 就是一个多余的摆设字段；历史版本 git 管得比我们自造的字段更可靠。
- **放弃的方案**：保留 `archived` 字段继续用。
- **依据**：commit `6559f18`（删引擎）、`1f11fde`（清过时 archived 状态）。**以后在旧代码里看到 "archived"，别当缺了什么把它加回来。**

### D-05 阶段上下文工具只归 `stage_context_cli`

- **背景**：每个生产阶段之间靠"启动包 / 审核包 / 交接 / 校验"传递上下文，这些工具入口分散，容易被绕过。
- **决定**：阶段间只用 `scripts/stage_context_cli.py` 的 `prepare` / `review-pack` / `handoff` / `validate`；不另起炉灶、不让通用插件或通用视频能力接管。
- **为什么**：统一、确定性、可校验，避免每个 AI 各用一套传递方式导致漂移。
- **放弃的方案**：用通用聊天对话或直接拷文件来传上下文。
- **依据**：[PROJECT_RULES.md](../PROJECT_RULES.md)「工作边界」。

### D-06 当前产物增量修正，长期提炼另行维护

- **背景**：边做片子边改、边写知识库，重读大图会撑爆上下文，引发故障链（和 R-05 同一类问题）。
- **决定**：用户已授权的当前候选修正继续执行，同一候选增量复审回原审核对话；已确认产物返工另存版本。非阻塞的工具改造、长期规则提炼在收尾后另行授权维护；上下文过重时再用最小交接转入干净对话。生产 Skill 不顺带写知识库。
- **为什么**：干净上下文里复盘修正才不会污染、才不会带回旧的烂摊子；提炼放在修正之后，教训才准确。

### D-07 产物归属：桌面 = 工作区，知识库 = 只读归档

### D-08 测试保持最小充分，使用可用的 pytest 环境

- **背景**：曾有 29 个冗余测试 + 大型套件；本机默认 `python` 是 3.12（无 pytest），pytest 只装在 3.13。
- **决定**：保留小而有效的核心测试，按当前改动风险和未决问题增减，不以历史数量 8 作为上限或验收目标；优先使用已安装 pytest 的 Python 3.13，实际以当前环境核验为准。
- **为什么**：不为防回归而加测试体积（个人工具不值得）；环境差异已经踩过坑，记住用对的解释器。
- **放弃的方案**：扩成完整测试套件；直接用默认 python 3.12 跑。
- **依据**：commit `6559f18`、[README.md](../README.md)「环境」；memory `pytest-lives-in-python313`。

### D-09 提示词语言合规 = 跨 skill 共享红线

- **背景**：给"造物者抛光面膜2.0"写资产母图提示词时混入"影视级、8K"这类**炫技含糊词**。根因两层：一是 asset 方法把"读提示词规范"标成**"涉风险才读"**（作者因此跳过、没读就写）；二是现有的空白/上下文审查里**没有"提示词语言合规"这一条**，漏了也拦不住。
- **决定**：把"凡写提示词必合规范 + 按本 Skill 方法写 + 交付前必审"设为**跨 skill 共享红线**（`skills/_shared/prompt-language.md`，第六类红线），并给会写提示词的 4 个 skill（`asset-image-assistant` / `storyboard-director` / `voiceover-to-video-script` / `blender-previs`）各接三处：**① SKILL.md 读取清单**（五项共享红线→六项，加 `../_shared/prompt-language.md`）、**② 模块方法**（把"读提示词规范"从可选变强制）、**③ review-profile.json 加 `PROMPT-LANG` 检查**；同时立即清掉当前资产提示词里的"影视级/8K"等。
- **为什么**：它天然是**跨所有写提示词步骤的通用红线**——逐 skill 补等于每次漏一个、永远追不齐；接进 review-profile 后审查自动兜底，漏洞才拦得住。这也符合项目既有分层：`_shared/`＝红线（只定不变原则）、`skill/modules/`＝执行方法、`skill/references/`＝专业规范、知识库＝专业正文；红线不规定读哪个文件、怎么写。
- **放弃的方案**：① **"逐 skill 补"**——每出一件事补一处，无法一次到位，且不同 skill 各自维护易漂移；② **"先加 hook 全局强制"**——用 hook 强制"写提示词必读库 + 必审"虽可硬保证，但触发规则难定、易误伤其他文本；当前"共享红线 + 审查兜底"已够，hook 留作**可选增强**，本次不加。
- **依据**：`skills/_shared/prompt-language.md`；[2026-09-06_提示词语言合规_执行单.md](2026-09-06_提示词语言合规_执行单.md)；KB 复盘 `wiki/projects/Master-Storyboarding/2026-09-06_提示词语言合规治理复盘.md`；commit（本次改动，见 git status）。

### D-10 知识驱动产出设为强制门禁：先 prepare + 命中规范，缺规格即停

- **背景**：给"造物者"系列出资产图时，`asset-image-assistant` 阶段**没先 `prepare`**（当时的 `stage_startup` 还是上一个 skill 的），该阶段没有自己的知识包；而 `knowledge-access.md` 又规定"不扫整个 Vault"，于是**没包可读又不许自己扫 → 无回退 → 只能自由发挥**。加上有些 skill 把"读规范"标成条件性/可选（"涉风险才读"），且各类产出的"必须命中规范"没有写死、可查 → 有的环节查知识库、有的环节自己写。
- **决定**：把"**每阶段必须先 `prepare` 拿到知识包 → 产出前核对命中的规范 → 按适用性核对动态规则与本地规范，缺包自行准备，真实阻塞才暂停**"设为**跨所有生产 skill 的强制流程**：
  1. `stage_context_cli.py` 新增 `ensure-prepared` 产前门禁子命令：校验 `stage_startup.md` 存在、`# 阶段启动包`、`Skill 匹配`、知识包完整；未 prepare / Skill 不符 / 包不完整 → 报错并提示先 prepare。
  2. `skills/_shared/knowledge-access.md` + `PROJECT_RULES.md` 写入共享红线："任何生产 stage 必须先 prepare；未通过 `ensure-prepared` 不得产出。输入齐全时自行准备并重检，重复失败、真实输入缺失或 confirmed 冲突时才暂停。本地规范直接读取，不重复嵌入知识包；程序通过不等于 Agent 已阅读或完成合规审查。"
  3. 每个生产 skill 的 `modules/<方法>.md` 开头加"**本 Skill 产出须命中的规范（缺即停）**"清单，点名该 skill 必须命中的知识库/repo 规范，并把"涉风险才读"换成强制必读。
  4. 会产出图/提示词/分镜的 6 个生产 skill 的 `review-profile.json` 加 `KB-COMPLIANCE` 检查（审查兜底）。

### 隔离运行依赖只能由当前解释器持有（2026-09-21）

- **背景**：仓库同时被两个解释器使用——项目 Python 3.13（测试与确定性工具）和 Codex 内置 Python 3.12（视觉资产库服务）。
  `visual_asset_library.py` 只要发现 `.master-storyboarding/visual-library-deps` 就无条件把它插到 `sys.path` 最前面，
  而这个目录是 3.12 装的（`rpds.cp312-win_amd64.pyd`）。3.13 下 `import jsonschema` 因此被抢到坏副本上：
  一次全量测试从 363 通过变成 97 失败/258 通过，资产 schema 校验统一报"运行结构化合同校验需要 jsonschema"。
  根因不是"目录脏了"，而是**装的人没留痕、用的人不校验**。
- **决定**：新增 `scripts/core/runtime_deps.py` 作为第三方依赖的唯一解析出口：目录带 `stamp.json`（解释器版本、平台、
  依赖清单哈希）且全部匹配才使用；带 stamp 但不匹配一律弃用（绝不试探性加载）；没有 stamp 时才用当前解释器起隔离子进程
  逐个 import 目录里的顶层包，要求解析结果确实落在该目录内。新增 `scripts/install_runtime_deps.py` 作为唯一安装/登记入口：
  一目录只属于一个解释器，已有他人 stamp 时拒绝安装，`--force` 才清空重建；未登记但当前解释器可用的旧目录只补写 stamp、不重装。
  `visual_asset_library` 改为调用 `ensure_runtime_deps()`，不再自己插路径。
- **为什么**：两个解释器共用一个绝对路径时，"可用性"是运行时的属性而不是目录的属性；只有让每次使用都按当前解释器验证，
  才能同时保证 web 服务（3.12 需要隔离依赖）和测试/工具（3.13 不该被 3.12 的二进制污染）。stamp 让常见路径零开销，
  隔离探测兜住未登记的老安装，fail-closed 让错配安静地回落到宿主环境而不是炸在某个无关的 import 上。
- **放弃的方案**：① 直接删掉隔离目录——会让 3.12 的资产库失去依赖；② 只删 rpds 的旧 pyd——下次换解释器再犯；
  ③ 把目录按解释器分开放（`deps/py312`、`deps/py313`）——要迁移已有安装与文档路径，收益小于 stamp 方案；
  ④ 运行时永远优先宿主 site-packages——宿主的 jsonschema 版本不受 `config/requirements.txt` 约束。
- **依据**：`scripts/core/runtime_deps.py`、`scripts/install_runtime_deps.py`、`scripts/visual_asset_library.py`、
  `scripts/tests/test_runtime_deps.py`（含"陈旧副本不得遮蔽宿主包"回归用例与"只有 runtime_deps 能插路径"边界用例）；
  提交见 git log。

### 用户确认范围只有一个判定权威（2026-09-21）

- **背景**：`PROJECT_RULES.md`「逐场创作与确认」规定了机器确认记录的 `scope`/`scope_description` 字段，但代码里
  只在 `artifacts._whole_artifact_receipt()` 内联了六个 id 字段的黑名单，既没有产出入口也没有校验入口；规则和实现各写一套，
  逐段确认只能靠手写 JSON，写错（例如把 `shot_ids` 写成字符串）不会被拦下，反而可能被当成整稿确认。
- **决定**：新增 `scripts/core/confirmation_scope.py` 作为唯一权威：分类（artifact/segment/dialogue/unscoped/legacy-text）、
  写出前严格校验、只读审计三合一；`artifacts` 只做转发；`revision_control.record_scoped_confirmation()` 是逐段/对白确认的
  机器入口，只写记录、不推进变更案状态；`commit_change()` 增加"只有整稿范围确认才能提交"的防线。判定 fail-closed：
  出现任何局部编号字段（哪怕值写错）、非整稿 kind、无法识别的 scope 文本都不算整稿；没有 `scope` 的老记录要按整稿兼容，
  但必须至少带一条确认凭据（`artifact_ids`/`artifact_id`/`approval_ref`/`confirmation_ref`），空对象与事务回执不再被误认可。
- **为什么**：范围是"这次确认覆盖到哪里"的唯一事实，必须一个出口说了算；把产出、校验、审计放在同一模块，规则文本只需指向它，
  再不会出现"规则写了字段、代码不认"的漂移。fail-closed 保证不确定时不会把局部确认升级成整稿凭据。
- **放弃的方案**：① 继续在 `artifacts` 内联黑名单——每加一种范围就要改一处、规则仍无对应实现；② 在 `confirm_candidate` 上
  加 scope 参数——那会把局部确认混进"整稿采用"的提交链，语义错误；③ 增加独立的 scope schema 文件——现有确认记录是项目内
  JSON，没有进入 schema 校验链，多一个文件只会多一处要同步的地方。
- **依据**：`scripts/core/confirmation_scope.py`、`scripts/core/artifacts.py`、`scripts/core/revision_control.py`、
  `scripts/tests/test_confirmation_scope.py`；两个真实项目只读审计：王总饭局 25 条记录 0 结构问题、当前产物 4/4 仍确认；
  顶级财阀 7 条记录 0 结构问题、当前产物 5/5 仍确认。
