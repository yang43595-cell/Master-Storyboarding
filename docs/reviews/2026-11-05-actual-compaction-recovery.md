# 真实上下文压缩后的规则恢复实测

日期：2026-11-05（Asia/Shanghai）。对象是本地工作树中的项目规则。实验只读，未运行真实业务生产、图片或视频生成、上传、发布、采用或人工确认。

## 测试方式

使用本机已安装 Codex CLI 的真实 app-server，创建 `ephemeral=true`、`sandbox=read-only`、`approvalPolicy=never` 的隔离会话，沿用本机默认模型 `gpt-6.1-sol`、`medium` reasoning effort 和 `openai` provider；回包核 sandbox 为 readOnly、networkAccess=false。没有修改默认模型、账号配置或用户当前主聊天，没有复制摘要冒充压缩。

每轮均在同一 thread ID 内执行：

1. 压缩前，通过真实工具读取 AGENTS、总规则及本题适用细则。
2. 调用真实 `thread/compact/start`。
3. 等待 `contextCompaction` 的 `item/started`、`item/completed`，并核压缩 turn 的 `status=completed`。
4. 对同一 thread 发恢复请求，要求按项目恢复入口补读原文；记录恢复后的实际命令、答复和未决状态。

接口语义核对依据：[官方 App Server 说明](https://developers.openai.com/codex/app-server/#trigger-thread-compaction)。完成事件、同线程标识和后续工具读取来自本次本机实际回包，不是文档推断。恢复请求明确提示按项目恢复规则重新读取，因此这是**有恢复指令的实测**，不是无提示自动恢复能力实验。

## 首次脚本故障与证据

最早一次试跑在压缩前被本地测试脚本的 64 KiB 单行读取上限阻断并超时；待收命令的来源输出约 89 KB，尚未获得压缩完成事件。首轮失败结果保留，没有算入压缩通过次数。将事件读取缓冲上限改为 8 MiB 并显式传播读取异常后，使用相同默认模型与核心题目重测，得到上述真实压缩完成回执。

本轮脚本和证据保存在源码仓库之外；没有为测试修改规则、生产代码或真实业务项目。测试依据只覆盖当前工作树与这些题目，不证明全部规则永不遗漏、多次压缩或上下文极限下的表现，也不等于实际生产链已经执行通过。
