# 怎么用它做一部短剧（个人使用说明）

> 一句话：这是用 AI 帮你把「一个故事 / 主题」做成**分镜、资产、视频脚本、成片**的流程。共 **7 步**，新创作轮由干净的专属执行者完成并自查，主对话协调；独立审核仅在明确要求时启动；你确认且明确继续后进入下一步。

当前统一流程按[审核到画布入口](review-to-canvas-entry.md)执行：编导和资产图由网站人审，下游按授权自行验收，最终保存画布草稿。下文逐阶段人工确认说明保留为兼容路径；图片制作按[图片生产批次](../../PROJECT_RULES.md#图片生产批次)交给干净子 agent，每批最多 8 张，普通准备使用[独立批次上下文](../../skills/_shared/knowledge-access.md#图片批次的隔离准备)。

## 先记住两件事

1. **通常是「生成启动包 → AI 干活 → 你审核 → 交接到下一步」**；视频提示词阶段按 Skill 直接读取和自查，不创建准备包、阅读凭据或审核包。
2. **三种状态别混**：`候选`（AI 做出来的，还没定）→ `审核通过`（审核口头认可）→ `你确认`（你点头，才算数）。只有你确认的版本才会进下一步。

新电脑或新 agent 先按 [独立仓库启动](standalone-repository.md) 核验。以下命令中的 `--vault` 可省略，此时使用仓库内已选方法，不需要 Mac 或 Obsidian。

## 一、建项目

在你桌面建好，或在命令行运行：
```powershell
python scripts/init_desktop_project.py --path "C:\Users\LIUYANG\Desktop\项目名"
```
建好后有 9 个目录：`00_项目管理`、`01_原始资料`、`02_编导`、`03_导演`、`04_资产`、`05_分镜`、`06_视频`、`07_声音与配音`、`99_历史与废弃`（以 `scripts/init_desktop_project.py` 的 `PROJECT_DIRECTORIES` 为准）。项目事实存在 `00_项目管理\project_state.json`。

> **旧项目保留旧目录名**，例如 `01_脚本与分镜文档`、`02_正式分镜图`、`04_视频_正式片段`、`06_参考帧与临时素材`、`07_声音与配音`。工具仍按旧名兼容读取（`visual_asset_projects.py`、`production_plan.py` 都有兼容分支），**不要为了改名去搬动旧项目的文件**。

## 二、7 步流程

| 顺序 | 技能（skill 名） | 产出 | 你主要审什么 |
|---|---|---|---|
| 1 | `creative-director` 编导 | 编导稿 + 叙事包（故事/对白/资产需求） | 故事、人物、对白对不对 |
| 2 | `storyboard-planner` 分镜 | 分镜方案 | 镜头、调度能不能拍 |
| 3 | `blender-previs` 预演（可选） | 导演预演 | 空间/调度预演 |
| 4 | `asset-image-assistant` 资产 | 人物/场景/道具/产品母版图 | 一致性、产品是否用真实参考 |
| 5 | `voice-reference-manager` 声音（可选） | 声音参考库 | 声音来源授权 |
| 6 | `storyboard-director` 画面补充（按需） | 正式分镜图 | 画面连续性 |
| 7 | `voiceover-to-video-script` 视频脚本 | Seedance 执行脚本 + 成片 | 提示词、成片 |

## 三、每一步怎么跑

选用白模后，可先让 AI 导出快速三维预览，再在已有资产网页“项目资产 → 白模预览”中查看机位、站位与运动并提出调整；支持自由观察、俯视和时间轴。正式参考仍按需渲染、检查和确认。具体入口见 [白模项目接入](../../skills/blender-previs/references/项目接入.md#同源网页快速预览)。

**① 生成启动包**（告诉 AI 这步要干嘛、要用哪些知识、项目现状）：

以下准备、阅读登记与审核包命令不用于 `voiceover-to-video-script`；该阶段的旧入口会明确拒绝。视频阶段直接按其 [Skill](../../skills/voiceover-to-video-script/SKILL.md) 读取已确认来源并交付提示词。

```powershell
python scripts/stage_context_cli.py prepare --project <项目路径> --skill <技能名> --objective <这步目标> --vault "C:\Users\LIUYANG\Documents\Obsidian Vault" --request-json <本轮请求JSON路径>
```

`--objective` 是目标说明，实际选知使用 `--request-json` 和项目摘要。请求由 AI 按当前已明确需求准备，沿用已有请求文件即可，不需要用户手写 JSON。只保留本轮任务与适用条件；历史方案、否定和输入矛盾的处理见 `skills/_shared/knowledge-access.md`。没有任务特定选知需求时可省略请求文件，但不能据此认为目标中的关键词已参与匹配。

例如已明确需要评估连续事件超时拆段时，请求可以是：

```json
{"task":"核对同一连续事件精简后仍超出已选模型限制的强制拆段条件"}
```

它仅用于查找相关规则，不确认导演包、不选择模型，也不授权拆段或生成。准备后仍须核对规则适用条件；必需规则缺失时使用现有 `ensure-prepared --required-rule <规则ID>` 检查。

**② 按当前分工执行**：新一轮编导、导演稿、视频提示词等实质创作交给全新、专属生产执行者，读取准确来源、对应 Skill 和适用方法后完成候选与自查；普通 prepare 阶段还须读取本次 stage_startup.md。主对话协调范围和检查结果，同轮逐段推进与返修续用该执行者，不递归派生产者。普通问答、只读审计、机械维护不因此新增执行者；环境与授权边界以 PROJECT_RULES.md 为准。

**③ 用户明确要求独立审核时准备审核包，再交你确认**：`prepare` 生成的 `task_basis.json` 是本轮交付对象、非目标、输入版本和适用标准的唯一依据；审核包只从它派生，不能另选标准。
```powershell
python scripts/stage_context_cli.py review-pack --project <项目路径> --skill <技能名> --artifact <候选文件>
```

需要项目特有检查时，在 prepare 的 request JSON 以 `review_checks` 冻结；`review-pack --check` 不再临时加标准。审核 Skill 本身的合同而非项目候选时，使用同一接口加 `--review-kind skill_contract`；它只读取同一任务依据中冻结的合同清单，不能与 production 结论混用。复审中任务依据或审核类型改变，必须作为新首审处理。
独立审核仅在用户明确要求时按 PROJECT_RULES.md 启动；首次使用空白 stage-reviewer，只读检查明确范围。修订由当前执行者负责；确需复审时用 review-pack --review-mode revision 回原审核者。审核通过不等于你确认；图片视觉质量仍由你终审。

**④ 交接下一步**（你确认后才做）：
```powershell
python scripts/stage_context_cli.py handoff --project <项目路径> --to-skill <下一技能名>
```
你确认且要求“继续／下一步”后，按下一 Skill 的实际入口准备；新创作轮仍用全新专属生产执行者，视频阶段不建启动包。只生成交接卡不代表已执行下一步，也不授权付费生成。

**⑤ 修正与收尾**：用户已授权的当前候选修正直接继续，同一候选增量复审回原审核对话，只核对修订项及直接影响；已确认产物返工另存版本。非阻塞的工具改造、规则沉淀放到收尾后，由用户另行授权 `knowledge-maintainer` 维护，不因交付完成自动写知识库。新创作轮的干净上下文要求不以主对话是否过重为条件。

## 四、红线（AI 必须遵守，你不用管细节，跑不过就说明有处不合格）

- 产品外观、包装、人物/服装、道具、产品镜头，**必须对照真实参考图**，不许 AI 按印象乱猜。
- 人物/场景/道具**跨镜头保持一致**，不得变来变去。
- **别把大图片或 Base64 塞进上下文**（费 token，也容易出问题）。
- **不覆盖已确认产物**；改已确认的前序内容属大动作，谨慎。
- 候选 ≠ 审核通过 ≠ 你确认，**只有你确认的才进下一步**。

## 五、校验

跑校验看有没有 ERROR（有就说明某处不通过，要修）：
```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/validate-project.ps1 -ProjectPath <项目路径>
```
项目状态、生产计划、Seedance 提示词等还有专门的校验脚本，跑不过会明确报错。

### 工作区重置后的核验

旧验收报告和绝对路径只作历史记录，不证明当前入口还在、源文件仍相同或模块已实际加载。先在新隔离目录按[源码恢复步骤](recovery-verification-20261018.md#reusable-recovery-procedure)恢复并核对当前授权基线；不要覆盖原项目或把旧启动脚本的成功记录当本轮执行。

从本轮实际入口运行检查，保留解析后的源码根、解释器与关键已加载模块的 `__file__`，对照本轮核定源码的字节；仅看到入口元数据或链接存在不足以证明实际执行。没有 Git 元数据的快照明确标为源码快照，保留原始 tree/blob 核验依据，不把本地重建提交冒充远端提交。

再从本轮准确业务 JSON 发现当前依赖，报告真实缺失/漂移；历史来源保留可追溯，但不得借恢复去删活动引用、补造原图或继承旧确认。运行现有检查时同时核退出码和返回结果、覆盖数量：零文档或未识别正文是“未检查”，不是通过；只有候选登记也不是正式采用。方法全文、实际看图/试听与适用动作仍由执行者完成，不由路径存在或程序通过替代。修复环境后重跑相同范围，分别记录通过、失败、未运行和仍被阻塞的生产步骤。

### 可重复的恢复入口（只读验收）

源码恢复继续使用标准 Git bundle，不新增项目账本。先核可信交付包完整性与其中准确源码 tree；在新目录 `git clone <已核验.bundle> <新目录>`。已存在目录不得覆盖；失败/重试先检查已有目录，核实准确字节后继续或选择新目录。源码树不包含外部方法、真实媒体、运行依赖或用户批准。

在恢复后的目录、选定的当前解释器中单独运行：

```sh
python -B scripts/verify_workspace.py --expected-tree <已核定40位Git-tree-SHA>
python -B scripts/verify_workspace.py --expected-tree <同一SHA> --project <准确项目根> --require-file <现行业务JSON> --input-root <明确外部输入根>
```

不得从“最新”文件名猜基线；传入的是 tree，不是 commit。命令先核全部登记源码和入口自身，再刷新依赖选择缓存、实际导入并核已加载源码路径/字节；损坏 stamp 对应的依赖不能沿用旧安装通过。版本与 requirements 指纹会报告，兼容性仍按准确 requirements 安装并运行测试，不把可导入等同所有版本/API 均兼容。缺失依赖按原 `install_runtime_deps.py` 修复；不会自动覆盖、安装或提升权限。

业务分支复用 `discover_dependencies(..., verify_hashes=True)`，只核所选依赖及同一明确文件上的 `path/path_or_url/file + sha256/checksum`。错字节、非法/冲突 hash、歧义路径失败；无 hash 的文件明确列 `unhashed_files`，只证明字节存在，不证明历史准确版本，不能补造旧 hash/确认。未提供业务输入时记 not_requested，不声称完整项目已恢复。报告是本次检查结果，不是新的业务权威；始终 `production_ready:false`，平台绑定与用户批准另核。

## 六、整片收尾

本仓库没有受支持的整片归档入口或完整搬运合同。`knowledge-maintainer` 只负责项目知识治理，不负责把项目整体搬入 Vault、同步文件或清理桌面源目录。不要根据本说明执行搬移或删除；需要整片归档时，应先指定已授权的归档流程和目标。上文的阶段内旧稿归档规则仍按其原有范围执行，不等同于整片归档。

## 七、给你的使用习惯

- **遇到问题先记下来，别边用边改。** 只修「挡着你出片」的；「内部不顺眼」的记到问题本，等有空再说。
- 生产阶段按上面的 7 步执行。需要维护项目知识入口或仓库合同，再单独授权 `knowledge-maintainer`；整片归档流程目前未在仓库定义。
