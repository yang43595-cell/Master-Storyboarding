# 知识生命周期与冲突处理

用户于 2026-09-08 授权调整 LLM Wiki 架构，减少重复、冲突及过期知识对 Agent 判断与项目取知的干扰。本页是这一维护流程的唯一正文；启动条件只在 [[agent-index]] 维护，写入服从根 [[AGENTS]]。

## 管理对象

知识正文继续保存在原主题页。原始资料和来源页保留出处及原意，来源重复表达观点不等于多份独立证据，也不等于应删除的知识重复。导航只负责定位，不能成为另一份当前规则。

| 对象 | 处理方式 |
|---|---|
| 同一来源再次摄入 | 按规范化网址、来源编号或实际原文核对；复用来源页 |
| 同一结论再次出现 | 优先给主题主版本补来源、反例或适用条件；不另建同义综合页 |
| 到了复核日期 | 进入待复核；日期本身不证明错误 |
| 同一对象、同一时期及适用条件下出现不相容主张 | 记录争议双方，核验后裁定；相似度只能帮助找候选 |
| 已由证据推翻 / 被新结论替代 | 从当前依据退出，保留原因、证据及替代关系 |
| 历史记录、已完成项目、来源引用 | 按当时语境保存；当前检索不把它们升级为现行结论 |

## 触发和工作量

1. **摄入前**：围绕新资料的对象和关键主张检索已有主题。结果不足再按检索治理扩展；只更新新证据确实影响的页面。
2. **使用前**：已知目标页先检查状态；未知目标先查询候选。待复核知识若影响当次判断，核对来源、版本或运行证据；不能把检索命中或旧 `verified` 标签当成已重新验证。
3. **明确的整理任务**：按主题扫描，集中处理有限的一批问题。先处理真实冲突、已失效入口和高影响事实，再处理缺少复核信息的旧页。没有启动常驻服务或定时自动化。
4. **处理完成**：再次查询或检查目标，确认当前依据已更新，并说明仍需人工或项目流程处理的事项。

普通提问不自动产生新综合页。没有新结论、证据、适用条件或关系变化时，维持原页；保存回答仍需已有摄入/维护授权或用户明确要求。

## 判断与解决

### 去重

同义词、标题、正文相似度和同一 `key` 只用于定位候选。比较结论、作用域、证据来源及新增细节后，选择：补充原页、合并冗余表述、保留不同条件的结论，或登记冲突。多个转载同一原始来源不增加独立证据权重。不同来源的原文仍可各自保存。

去重不得丢掉独有案例、失败条件和来源。合并正式主题页时留下替代入口，修正当前导航；没有必要批量改名或搬移历史。

### 过期

软件能力、价格、配置等易变事实记录核验日期及版本/对象。`review_after` 表示下一次应核验的日期；`updated` 或文件修改时间不作为核验日期。长期稳定的方法不强制按固定天数失效；反例出现时先检查适用范围。日期未知就标未知，不从文件时间推造事实有效期。

复核结果可为：仍适用（更新核验日期及证据）、需要缩小适用范围、证据不足（继续待复核）、已被替代、已被推翻。一次成功或失败不自动建立或推翻通用规则。

### 冲突

逐项比较对象、属性、项目/机器、版本、事实发生时期、适用条件和来源。不同版本、不同项目或例外条件可能同时成立；发布时间更新不自动胜出。规则另按指令层级及项目作用域处理，不能用外部资料修改用户授权。

真实争议要有双方原文位置、为何不能同时成立、新证据及当前处理理由。无法裁定时保留 `disputed`，回答时说明分歧，不让它静默混入确定结论。影响执行的规则冲突交回适用项目流程。

## 状态与正文

原 `status` 继续表示知识成熟度和确认情况；新增可选 `lifecycle` 表示本轮使用和复核状态，两者独立。缺少 `lifecycle` 的旧页输出 `legacy_unreviewed`，不假定刚刚核验，也不因字段缺失整库停用。

| lifecycle.state | 当前使用 |
|---|---|
| `current` | 可参与判断，仍受页面状态、作用域和证据约束 |
| `needs_review` | 待核验，影响当次判断时先核验；不等于错误 |
| `disputed` | 不作为无争议结论输出，必须展示争议提示 |
| `superseded` | 已被替代，仅追溯；必须有替代入口、原因和证据 |
| `invalid` | 已被推翻，仅追溯；必须有原因和证据，可以暂无替代 |

工具同时识别原有 `status: deprecated/archived/draft/candidate`、`retrieval.default: excluded`、顶层 `review_after` 和 `superseded_by`。旧状态不会被 `lifecycle.current` 覆盖。坏元数据、失效或含糊的替代链接必须可见，不能默认为当前有效。

页级示例（按真实情况填写；不要给每一页机械复制）：

```yaml
lifecycle:
  state: needs_review
  key: 某工具.某能力
  scope: [某工具版本, 某项目或机器]
  reason: 新版本资料与当前记载不一致，尚待核验
  evidence: ["wiki/sources/已存在的来源页.md"]
  review_after: 2026-09-08
  conflicts_with: ["wiki/entities/已存在的相关页.md"]
  depends_on: []
```

`reviewed_at` 仅在实际复核后填写。`superseded_by` 指向真实替代页；`depends_on` 只登记“这个结论依赖该依据”，普通相关链接不填进去。新关系优先使用完整 Vault 相对路径，避免同名误解析。

一页包含多个独立结论时，只给需要追踪的段落使用可选的 `kb-claim` 原地块。正文仍只有一份，JSON 中不重复保存结论全文；不要求全库拆卡。块属性与 `lifecycle` 相同，另有唯一 `id`：

````markdown
<!-- kb-claim
{"id":"KB-示例-001","key":"某工具.某能力","scope":["某版本"],"state":"needs_review","reason":"出现新版本，尚待核验","evidence":[]}
-->
## 某个需要复核的结论

这里保留原结论和适用条件。复核结果在此原地维护。

<!-- /kb-claim -->
````

废弃块要在正文附近保留人可读提示。直接打开整页的人仍能看见历史，工具只能过滤经它输出的内容，不能拦截宿主任意文件读取。

## 使用工具

`tools/knowledge_lifecycle.py` 是本地只读入口。它读取当前 Markdown，没有另一份永久知识正文，也没有持久搜索缓存；不调用模型、不联网、不修改页面。现有可用解释器是 Python 3.13 / PyYAML 6.0.2，普通 `python` 可能指向不含 PyYAML 的 Python 3.12。

```powershell
$kbPython = 'C:\Users\LIUYANG\AppData\Local\Programs\Python\Python313\python.exe'
$kbVault = 'C:\Users\LIUYANG\Documents\Obsidian Vault'
& $kbPython "$kbVault\tools\knowledge_lifecycle.py" query --vault $kbVault --scope 'wiki/concepts' --query '连续性 衔接' --limit 5
& $kbPython "$kbVault\tools\knowledge_lifecycle.py" check --vault $kbVault --path 'wiki/concepts/02-镜头与剪辑/段间重叠衔接.md'
& $kbPython "$kbVault\tools\knowledge_lifecycle.py" intake --vault $kbVault --query '新资料的对象和主要结论' --limit 5
& $kbPython "$kbVault\tools\knowledge_lifecycle.py" scan --vault $kbVault --scope 'wiki/entities' --limit 10
```

结果包括候选、警示、问题及扫描覆盖范围。`query` 默认选当前知识层；来源可用 `--include-evidence` 纳入并标明身份；显式 `--scope projects/项目名` 配合该参数也能查询该项目记录作为证据，不授予执行权。`--history` 用于明确的追溯，默认仍只扫描 wiki，归档或 raw 需显式指定 scope。`check` 也适用于从 `rg`、导航或历史任务直接得到的目标页；已经掌握定位无需再做一次全库搜索。同一任务已检查且文件未变时不重复检查。

`scan` 和 `intake` 只能生成待核验候选；同主题/同 key 不等于已确认矛盾。完全相同的知识正文可在结果中折叠并保留全部路径，不把重复算作多票。关键词检索可能漏掉同义表达，仍需按检索治理回退；无命中不能证明不存在。

第一版工具不自动识别所有语义重复或矛盾：相同作用域和 key、完全相同正文、相同来源编号/规范化网址提供候选；`conflicts_with` 表示尚未解决的显式争议。复核已解决后清除活动争议关系，历史理由保留在正文记录。到期列表与缺字段覆盖统计分别输出；既有字段不足不解释为全库健康。

## 下游处理与写入

原结论被修订后，检查明确的 `depends_on` 及 `sources/upstream`、正文引用。工具检查明确依赖；其余链接只帮助定位人工检查对象。引用失效知识的页面得到“可能受影响”提示，不能自动连带宣判整页错误。

处理记录至少有目标路径或编号、旧主张、新证据、决定、原因、替代入口及受影响入口。记录放在原页的复核说明或项目现有审计中，不建立复制正文的中央裁决库。重要变化沿现有 `wiki/log.md` 或项目日志记录，范围服从 owner 白名单。

已授权摄入和事实修订使用现有相应 owner。工具和治理规则修改在独立 Worktree 完成；没有适用写入范围时不自行扩权。未解决项可作为本次报告交付，不为存一条提醒增加跨目录写权限。普通扫描不写库、不提交。

## Master-Storyboarding 边界

已有 `msb-knowledge`、`canonical_key`、`authority=wiki/repo` 和项目选择器继续生效，通用工具提示交给项目入口处理。不能把它改成另一套通用规则块，也不能通过普通正文绕过项目选择器。

本通用工具用于知识维护、普通查询及问题溯源，不插入每次项目 prepare 或阶段冷启动。项目现有启动包继续按其明确入口生成；本次未修改外部执行仓库。

失效处理遵循 [[wiki/reference/Master-Storyboarding/知识接入与生产反馈规则#生产反馈与无效规则处理]]：先溯源，确认因果，按既有用户确认要求删除目标块、保留来源和极简冷记录。冻结在仓库的合同要在执行仓库修订。历史定稿不自动返工。页面检查通过不等于项目启动包已更新，实际生效应在该项目入口验证。

## 验收标准

- 新资料出现时，能找到已有结论，并说清补充、重复或争议的依据。
- 到复核日期只产生待核验提示；修改时间、重复次数不改变真实性。
- 确认废弃的正文不进入当前工具结果，追溯能找到原因及替代页。
- 冲突被排除时同时返回警示，不把有争议伪装成无资料。
- 同页局部失效不隐藏无关有效段；普通链接不造成连带误废弃。
- 原文状态修订后再次查询立即反映，无需同步另一套永久索引。
- 接入本页的 Agent 能遵循流程；未接入的外部工具、旧任务上下文和项目冻结合同不声称自动受到控制。
