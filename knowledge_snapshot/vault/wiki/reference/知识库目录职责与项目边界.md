# 知识库目录职责与项目边界

> 本页是文件归属的唯一权威正文，由 [[agent-index|启动索引]] 定向读取。原启动索引的“规则 1：文件存放”合并于此；不自动迁移历史文件。

## 文件存放基本约定

所有项目知识与参考资料统一存放在本知识库中；代码、Skill 本体、配置、模板、脚本、测试和其他执行文件保留在对应项目或 Skill 的实际目录中。同一内容只保留一个主版本，其他位置只保留摘要和链接。

独立 suibi 插件的个人原话、行动状态和本地备份是例外，保存在 `C:/Users/LIUYANG/.local/share/codex-suibi/`；启动读取索引不等于展开或写入这些个人资料。只有明确要求知识导出时才按本页归档。

不因文件名含“参考”“设计”“计划”就决定目录。项目归属不明确、可能跨项目或规则冲突时先询问，不自行选择目录；已有授权明确允许暂存时才进入 `wiki/inbox/`。

## 一句话原则

文件的存放位置由两个维度共同决定：

1. 它是项目文档、项目知识、原始证据，还是可跨项目复用的知识；
2. 它处于探索、验证、运行或归档中的哪个状态。

因此，项目相关内容统一收在 `projects/`，**不在 `wiki/` 下另设项目层**；同一项目只有一个入口、一份正文，不做两层并存。

## 顶层目录职责

| 目录 | 当前职责 | 默认权威内容 |
| --- | --- | --- |
| `raw/` | 原始资料层 | 下载文件、转写、原始笔记、附件和其他证据；默认只读 |
| `资产库/` | 跨项目视觉资产层 | 分类保存可复用图片、原始参考、候选、历史版本及来源清单；界面代码与缩略图缓存保留在执行项目 |
| `wiki/sources/` | 来源知识层 | 按来源整理的摘要、出处、核心主张和风险 |
| `wiki/concepts/` | 通用概念层 | 可跨项目复用的方法、原则和判断框架；`.evolving.md` 为探索态 |
| `wiki/entities/` | 实体层 | 平台、工具、品牌、产品和组织等稳定资料 |
| `wiki/synthesis/` | 综合层 | 跨来源、跨领域的综合结论、比较和复盘方法 |
| `wiki/reference/` | 运行参考层 | 跨项目运行规范、治理和可复用参考；专业方法进入对应主题页。执行代码、Skill 本体和项目执行合同留在各自执行目录 |
| `projects/` | 项目层（Vault 根） | 各项目专属知识、工作流、实验、脚本库、素材管理、账号配置和项目复盘，以及 PRD、架构、计划、版本文档、审计报告和项目治理文档 |
| `archive/` | 历史归档层 | 已完成、终止或被替代的项目与资料；默认不参与普通检索 |
| `学习/` | 个人学习层（Vault 根） | 用户的内容与想法工作台：通俗学习稿、收藏理由、疑问及不同稿子间的关系；**不是知识库证据**，见下节 |
| `schema/` | 模板与结构层 | 文档、报告和知识卡片模板 |
| `tools/` | 工具执行层 | 捕获、报告、索引和其他自动化脚本 |

执行仓库、Skill 本体、配置、模板、脚本、测试和其他运行文件继续保留在各自项目或 Skill 的实际执行目录中。若执行目录在 Vault 外，项目总览只记录其路径，不把执行文件复制进知识库。

`raw/` 的常用子目录及其约定：

| 子目录 | 放什么 |
| --- | --- |
| `raw/articles/` | 网页文章、博客 |
| `raw/papers/` | 学术论文、技术报告 |
| `raw/clippings/` | Obsidian Web Clipper 输出 |
| `raw/transcripts/` | 会议、播客、视频文稿 |
| `raw/notes/` | 个人零散笔记 / 日记 → 作为 source 摄入 |
| `raw/assets/` | 图片等附件（在 Obsidian 设置中将附件路径指向此处） |

`wiki/` 的内部构成：`index.md`（主目录，每次摄入后更新）、`log.md`（操作日志，仅追加）、`overview.md`（顶层综合 / 首页）、`entities/`（人物、组织、平台、工具、产品等实体页）、`concepts/`（主题、思想、术语）、`sources/`（资料摘要，每份资料一个页面）、`synthesis/`（跨领域综合分析、比较、问答归档）、`reference/`（运行规范与辅助参考）、`inbox/`（待归类草稿）。`schema/` 放配置与页面模板。

## `projects/` 项目层的内容边界

`projects/<项目名>/` 同时容纳两类内容：

**相对稳定、需要版本管理的项目文档**——产品圣经、PRD、架构和技术设计；实施计划、当前版本和历史版本；审计报告、方向登记册和治理决策；项目级的正式交付说明。这类文件回答“项目的正式设计、约束和版本是什么”。

**持续变化、需要频繁检索、直接参与生产的项目内容**——项目事实、工作流、脚本库、素材库和账号配置；实验记录、案例、失败记录和复盘；当前项目的候选规则、操作清单和生产状态；面向某个内容项目或成片任务的阶段文件。这类文件回答“项目如何运行、做过什么、当前积累了什么”。

两类合在同一层而不拆分，是因为它们同属一个项目、读者和检索路径一致；在项目子目录内仍按内容性质各自编排，不因同层就混成一份正文。

项目入口按应用方法、项目事实、任务状态和案例记录分组。项目应用方法写清知识来源、采用条件、项目做法与检查方式；不复制通用知识全文，也不替代执行仓库的 Skill、模板和技术合同。案例与复盘按需读取，其中的建议不能因所在目录而自动成为现行方法。

明确退休的治理正文归 `archive/`。分类和迁移不改变原内容的确认状态，不代表已验证方法效果或完成 Skill 接入。

项目与项目之间、项目与通用知识之间通过项目注册表和 Wiki 链接关联，同一结论只保留一份主版本。

## 知识生长路径

```text
项目事实与实践
  → projects/<项目名>/
  → wiki/concepts/<主题>.evolving.md
  → 用户确认并完成验证
  → wiki/concepts/<主题>.md 或 wiki/reference/<领域>/<文档>.md
```

- 项目层记录“这次发生了什么”；
- `.evolving.md` 记录“它可能说明什么”；
- 稳定概念或参考页记录“以后可以按什么执行”；
- Skill 运行时只读取明确登记的稳定参考，不读取项目实验和探索文件，除非对应 Skill 明确声明读取条件。
- 专业知识正文留在 Vault；执行仓库保存工具合同、输入输出字段、技术检查及可产出模板。必要的执行约束只保留来源回链，不复制知识正文。
- Master-Storyboarding 的动态知识选择和 `enabled` 规则块以 [[wiki/reference/Master-Storyboarding/知识接入与生产反馈规则|项目接入规则]] 为准；这是该项目的特例，不要求其他项目采用相同流程。

## `学习/` 个人学习层边界（2026-09-25）

`学习/` 在 Vault 根与 `wiki/` 平行，服务对象是**用户本人**。它帮助用户快速理解长内容、保存自己的想法，并逐渐连接不同来源；`wiki/` 保存经过来源核对、可供后续检索复用的知识结论。

| | `wiki/` | `学习/` |
| --- | --- | --- |
| 服务的读者 | Agent 检索、项目复用 | 用户本人 |
| 放什么 | 结论、方法、来源摘要 | 通俗学习稿、个人问题与思考、稿子之间的关系 |
| 写法 | 精炼、去重、可追溯 | 为用户压缩长内容、讲清论证与限制，保留原始出处 |
| 与其他层的关系 | 不把 `学习/` 当证据 | 用户提出沉淀时回到原始来源核验，本层稿子保留 |

判定规则按用户意图，不只按资料类型：

视频、文章、课程、社媒收藏和个人想法都可能成为学习材料；视频也可能直接摄入 Wiki。不能因“是视频”就归入学习区，也不能因某份旧来源记录缺少摄入状态就推定它适合做学习稿。已有 Wiki 来源页时先核对并复用，不重复分类或建页。

1. 用户要“学会 / 看懂 / 做学习稿 / 收藏并整理 / 留下我的想法” → 写 `学习/`；长材料默认压成一篇给用户看的稿子。
2. 用户明确要“沉淀到 Wiki / 存进知识库 / 摄入为知识” → 按知识库摄入流程写 `wiki/`。
3. 只给链接且意图不明 → 默认先做学习材料；不自动把个人收藏或认可当成已核实知识。
4. 用户同时明确要求两者 → 分别处理，Wiki 仍以原始来源为证据，不以学习稿为证据。

两条硬边界：

- `学习/` 的页面**不构成知识库证据**，不被 `wiki/` 当来源引用，也不参与知识库的事实等级、复核与冲突判定；
- 沉淀只写经核对的结论和适用条件，不把个人看法或教学正文搬进 `wiki/`。

原片、文章原文、转写与来源记录留在 `raw/`；给用户读的稿子统一放在 `学习/学习稿/`，并链接回原始来源。`学习/` 还可保存个人记录，不把案例稿直接放在根目录。项目选题由所属项目结合目标和学习资料处理，不在学习层单设选题目录。执行正文是 `.claude/skills/study-material/SKILL.md`，学习稿结构校验是 `tools/study_material_check.py`；自动写入走 `content-ingest` owner。原始媒体沿用仓库既有忽略规则：磁盘保留、不入 Git；逐字稿与来源记录可入库。

视频来源记录用 `ingest_status: study_only` 标明“已做学习稿，暂不摄入 Wiki”，并用 `study_note` 指向真实学习稿。后续用户明确要求 Wiki 摄入时再核对原始来源，完成后改记 `ingested`。`excluded` 只用于已明确决定不摄入的资料，不用于暂缓摄入。只读盘点工具 `tools/raw_video_intake_audit.py` 将 `study_only` 单列为已处理，缺少状态的旧记录只报“待核对”，不直接断言未摄入；它不会建页或修改资料。

本次历史入库按用户要求复制，保留旧项目原图与引用；旧归档副本仅供原项目追溯，后续新增跨项目资产以资产库登记路径为正式保存位置，不同步覆盖历史副本。目录名、复制成功或文件名含“确认”均不自动构成新项目确认。

`资产库/` 的图片、资产索引和说明都只保存在本机知识库目录，不进入 Git。视觉资产网页使用独立文件写锁更新该目录，不受其他知识库任务的 Git 状态影响。该目录内的磁盘副本与网页本地资产记录用于恢复；它们不构成异地备份。

1. 原始资料只在 `raw/` 保存一份，项目通过来源页或链接引用。
2. 项目内容统一在 `projects/` 项目层；同一结论不复制成两份完整正文。
3. 通用知识进入 `wiki/concepts/` 或 `wiki/reference/` 后，项目页保留来源案例和适用边界。
4. 交付物保留在实际项目或执行目录；知识库保存交付说明、版本和位置索引。
5. 无法判断归属时先询问；仅已有授权覆盖暂存时可写 `wiki/inbox/`，不擅自移动既有文件。
6. 文件归属以本页为准，启动索引只负责定位；知识正文、执行合同各有唯一主版本，不在两侧复制维护。
